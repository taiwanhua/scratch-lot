# 協作偏好

這份是 repo 擁有者的協作偏好,Claude、Codex 與人員協作時都適用,所有 session / thread 都照這份做。本檔是正本;副本有兩處:本機 `~/.claude/CLAUDE.md`、Claude 專案的 Project instructions。改正本後,同步把全文貼到兩處副本。

## 接手時先讀

1. 這次要動的 repo 根目錄 `CLAUDE.md`,以及它指到的規範與流程文件。
2. 那個 repo 有 `docs/tmp/handoff-*.md` 就接著讀;沒有就讀 `docs/tmp/dis.md`(底座待辦)與 `docs/tmp/project-dis.md`(專案待辦)。
3. 換帳號、換電腦的接手流程見 `docs/agents/collaboration.md`「交付與換手」。

## 溝通

- 一律用繁體中文回覆,連一句短的進度回報也是;程式碼、檔名、指令照原樣。
- 文件與回覆要好讀:分節、條列、表格;每句主詞明確;不發明新詞,先查 `CONTEXT.md` / `CONTEXT-PROJECT.md`;縮寫要展開。
- 每個階段主動點名適用的 skill 或工具與用途,不假設使用者記得。
- 基礎設施操作(雲端資源、權限、DNS、CI/CD 設定)要逐步說明原理再給指令;先手動走一遍,確認每一步的結果,再自動化。

## 動手前

- **說「開始」(或「可以」「做吧」)才動手**:寫、改、刪程式碼、設定、文件、Figma、schema 前,先提方案(動哪些檔、怎麼改),等明確同意。問句、疑慮、建議都不是同意。純查資料、讀檔不受限。
- 提「待決定」之前,先查討論紀錄、規格與程式現有機制;回覆時逐條標「已定 / 延伸既有規則 / 新問題」。agent 回報的「需要決定」也一樣,查到答案就直接交回 agent。
- 分析與建議要先查證:讀程式找到入口,再實際跑取得數字。只靠推論的要明說「推論、未實測」,不能拿來要使用者決定。
- 方案先核對現況,優先延伸既有機制(STRUCT-13),不另做一套平行做法。
- 版本一律查 registry,不憑記憶。

## 進行中

- 同一份規格拆出的票,第一批獲准後,後續批次的合併、部署、派工可以自動接續;設計決定、規則衝突、非偶發的 CI 紅、需要使用者親自驗收時才停下來問。
- 冒出的小問題當輪就併入處理;release 前「之後再處理」的清單要清到 0。
- E2E 不自己觸發,交件時寫「建議跑 / 不必跑、理由」,由使用者決定。
- 有機密(token、密碼)的指令由使用者自己跑,機密不貼進對話。
- 權限被擋(auto mode 或權限規則)時不繞過,改給使用者一行 `! 指令` 自己跑;不自己改權限設定。
- 用完的開發伺服器、jest worker、背景程序要關掉;jest 預設 `--maxWorkers=2`。
- 成本敏感:預設選免費方案;派 agent 用 `model: "opus"`,使用者說額度到 90% 時新派的改用 `fable`,重置後換回。

## Claude 專案的 thread

- 要用 Figma、Chrome、部署腳本、repo 的 skill 或權限規則時,選 **Work locally**(本機 thread);純程式的小票才用雲端 thread。
- 常 commit、常 push 分支,額度或 session 中斷也不會丟工作。
- 重要的決定寫進 repo 文件,不依賴專案記憶(換帳號會看不到)。
