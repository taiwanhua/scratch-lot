# 資料範圍:規則產生器 + BaseRepository 統一執行

> 現況說明見 `docs/concepts/data-layer-and-isolation.md`「資料範圍規則」;api 介面與 JSON 形狀見 `docs/modules/data-scope.md`。

## 定位

**決策**:資料範圍與權限體系分離。權限管「進哪些頁、頁裡什麼能用」,資料範圍管「查資料時看得到哪些」。wildcard 只涵蓋功能權限,永遠不影響資料範圍。

**理由**:「能不能編輯」與「能看到哪幾筆」是兩個維度;綁在一起會讓每個角色都要為每種資料組合開一份權限。

## 機制

**決策**:

- 資料目標以 `(collection, moduleKey)` 為鍵:一個模組一個目標,同一張表可以有多個模組(所有表單模組共用 `form_submissions`)。每個資料目標一份規則設定;**沒有規則命中操作者 → 等於沒設定**(可見範圍內)。
- 執行時把同一 collection 下命中操作者的規則依 `moduleKey` 拼成 `$or`(沒有規則的模組只看可見範圍),固定欄位表只有一個 `moduleKey`,等於單一規則。規則只套模組資料表(`moduleData`)。
- 一條規則 = 套用對象 + 條件組合(巢狀 AND / OR 樹,任意深、UI 建議 3 層)。套用對象是**人員條件**(`@repo/domain/audience`,與流程審核者、知會、通知收件人同一種格式):頂層明確二選一 —「所有人」`{ mode: "all" }` /「符合條件」`{ mode: "match", filter }`;`filter` 是與條件組合同形的條件樹,欄位為使用者 / 角色 / 所屬組織(本身 / 含下層 / 含上層)/ 權限,只有「屬於 / 持有」,群組最多 3 層、空群組不允許。資料範圍的所屬組織只能指定組織(沒有單據或事件可代入)。
- 頂層合成可切換:OR(預設)取聯集;AND 取交集。只命中一條的人只受那一條限制。
- 執行在 BaseRepository 的查詢中介層,**最外層永遠 AND 租戶隔離保底**,不可關閉。含寫入與刪除。
- 套用對象由 `AudienceService.matchesAudience` 判斷,用這次請求已算好的事實:啟用中角色(`roleIds`)、所屬組織(`memberOrgIds`,含下層 / 含上層時再看組織樹),不是可見範圍也不是管理範圍(ADR-0005「管理範圍與可見範圍的分工」);權限欄只算**實際授予**的有效權限(停用的權限 / 模組 / 角色不算),不套超級管理員的略過。權限 key 全站一致,root 可以寫出跨租戶通用的規則(例:「有 `xxx.view-all` 的人看全部」)。
- 動態值算不出對象時 fail-closed:命中不到任何資料。
- 租戶差異化:套用對象的所屬組織指定租戶頂層並選「含下層」即可,不需額外表。
- 設定快取在記憶體(外層 collection、內層 moduleKey),儲存時作廢該 collection。
- 例外出口四個(建立者讀寫自己的表單提交、退役權限清理的跨租戶計數、審核流程對提交的系統讀寫、前置檢查的存在性判斷),登記在 ADR-0005「例外出口」。刪組織 / 撤銷開通的「無業務資料引用」以 `BaseRepository.existsAny` 問,不被規則收窄(fail-closed)。
- **對全員生效(套用對象「所有人」`{ mode: "all" }`)的規則也會收窄系統上下文**:系統上下文(`visibleOrgIds: "all"`、沒有角色與所屬組織)經 `BaseRepository` 讀模組資料表時,租戶保底放行、但對全員生效的規則照樣命中並收窄。所以「必須看到全部」的系統讀取不能靠系統上下文,只能走登記過的例外出口:`FormSubmissionUsageCounter`(退役權限清理的跨租戶計數)與 `WorkflowSubmissionStore`(審核流程,以 `tenantId` 為邊界)。
- **`workflow_instances` 掛 `moduleData`(有 `moduleKey` / `tenantId`),但禁止替它登記資料範圍目標**:實例是審核流程的權威資料,審核者與背景推進一律以系統上下文 + 明確的 id / `tenantId` 讀寫,讀取授權走 `canReadSubmissionRevision`;替它設規則會讓推進讀不到實例而卡住。

**理由**:

- 放在中介層才繞不過,與租戶保底同一個位置;看不到的資料也改不到、刪不到。
- fail-closed:規則設了卻算不出對象時,放寬比收窄危險。
- 快取:規則是低頻設定,每次查詢都讀規則太貴。

## 欄位目錄(seed 宣告)

**決策**:

- 各資料目標在模組 seed 宣告 collection、名稱、描述、可篩欄位;落庫到 `data_scope_targets`,`moduleKey` 由 seed runner 填宣告檔所在的模組。表單模組的欄位目錄 = 基礎欄位 + 提交狀態(表單自訂欄位不進條件)。
- 基礎欄位由底座自動掛進目錄(組織、建立者、更新者、建立 / 更新 / 刪除時間)。
- 型別決定 UI 與查詢翻譯,翻譯器不認識個別欄位:org / user / date / enum 四種。date 的值與表單引擎的日期同一種(選的那一天在租戶時區 00:00 的時點),整天的邊界以規則所屬組織(根組織)的租戶時區換算,同一份規則對每個操作者都是同一段時間,不另創一套日期語意。
- 動態值存佔位符,查詢當下代入。「僅本人」=「建立者 = 【操作者本人】」;「僅所屬組織」=「組織 = 【操作者的所屬組織】」。

**理由**:目錄由 seed 宣告,新模組不用改翻譯器;型別驅動讓 UI 與後端用同一張表決定運算子與值來源。

**現況**:date 條件是日曆天、逐租戶套用 —— 以根組織的時區把存的時點還原成那一天,再以操作者租戶的時區算整天的邊界;上面「同一份規則對每個操作者都是同一段時間」已不成立。

## UI

「資料範圍」頁在系統管理群組下,**根組織專屬**。左側是資料目標清單(一列一個模組,副文字是 collection),右側是規則編輯器(目錄驅動)。

## 取捨

- 快取在單一實例內;多實例之間要等各自作廢才一致。規則是低頻設定,現階段可接受。
- 規則只有「上限」,沒有「例外放行」。

## 預留不實作

**單筆分享**(把一筆資料分享給範圍外的特定人):需要模組宣告支援分享、一張分享關聯、查詢時多一個 OR。有真實需求再建。
