# 使用者與會員是兩套帳號體系:分表、分登入、分 token

> 現況說明見 `docs/concepts/accounts-and-tenants.md`。

## 帳號分離

**決策**:admin 的使用者(User)與 front 的會員(Customer)分 collection、分登入端點。JWT 的 `aud` 標記發給誰,拿錯的 token 一律拒。會員不進 RBAC:能力是固定集合 + 資料擁有權檢查。

**理由**:兩邊的憑證、生命週期與權限模型完全不同;混在一起,任何一邊的漏洞都會擴散到另一邊。

## 登入

**決策**:

- 短效 access token(HS256)+ 長效 refresh token(存雜湊,可輪替、可登出所有裝置)。
- 簽章演算法不寫入資料庫;第三方需要驗簽時改 RS256 + JWKS,只動設定。
- 密碼一律 argon2id 雜湊,統一用 `@node-rs/argon2`;seed 與 api 同一套件。
- 登入識別 = `account`;`email` 只用於信件流程。兩者在各自的表內唯一。
- 登入不可枚舉帳號:帳號不存在與密碼錯誤回同一個錯誤碼,**耗時也相同**。忘記密碼同理。

**理由**:

- 官方 `argon2` 套件的 Windows 預編譯檔在 Node 20 載入即崩;`hash-wasm` 是備案(純 WASM,慢 3–5 倍)。雜湊是標準 PHC 字串,跨實作可互驗。
- 只回同一錯誤碼不夠:「不存在秒回、存在慢一百毫秒」就足以用碼表分辨帳號是否存在。

## 多分頁:同一瀏覽器只會有一個登入者

**決策**:refresh cookie 是唯一真相,分頁記憶體只是它的快取;「誰後登入,全部分頁跟著他」。對齊用 `BroadcastChannel`,不做 `storage` 事件退路。「同時用兩個帳號」不支援。

**理由**:access token 在各分頁記憶體、cookie 全瀏覽器共用,兩者生命週期不一致;不對齊的話畫面會在沒有提示的情況下變成另一個人。BroadcastChannel 已是 Baseline 廣泛可用,兩套路徑並存要多一份去重與清 key 的邏輯,只換到 Safari 15.4 以前。

## 所屬組織與角色授予

**決策**:

- 固定用語:**所屬組織**(`org_user`)、**角色授予**(`user_role`)、**擁有組織**(`org_role`,每個角色只屬一個組織)。
- 使用者可同時屬於多個組織;token 只帶一個當前組織。
- **被授予角色的資格**:使用者的所屬組織中,至少一個落在角色擁有組織的子樹內。只在授予當下檢查一次。
- 跨租戶授予禁止;授予不改變所屬組織與可見範圍。
- 授予的防越權邊界見 ADR-0004「防越權與稽核」。
- 「組織外」:持有者的所屬組織皆不在該角色擁有組織的子樹內;授予照常有效,只在 UI 標示。

**理由**:下層組織的人直接被授予上層角色是常態(店員拿區域角色),不該要求先加入上層。只在授予當下檢查,避免組織異動時連鎖重算。

## 權限解析(聯集模型)

**決策**:功能面(可進的頁、頁內功能)取角色綁定的聯集;資料面由可見範圍與資料範圍規則決定(ADR-0005 / 0008)。當前組織不參與權限計算。v1 不快取,每次請求由單一入口現查。

> 現況:當前組織只用來剔除別租戶客製表單的動態權限,見 `docs/concepts/authorization.md`「表單模組的權限」。

**理由**:後台流量小,3 個索引查詢毫秒級;不快取就沒有作廢時機與多實例一致性問題,權限變更立即生效。日後量測到熱點再在 resolver 內加 LRU,呼叫端不動。

**已接受的副作用**:角色的功能可操作持有者可見範圍內其他分支的資料;要更緊用資料範圍規則收斂。

## 從組織移除使用者

**決策**:

- 移除所屬組織**不自動解除**角色授予。操作者三選一:全部保留 / 解除該組織擁有的角色 / 解除所有**失去資格**的角色(預設)。
- 失去資格 = 角色擁有組織的子樹 ∩ 移除後剩餘所屬組織 = 空集合。
- 後端 dry-run 逐筆列原因;選擇與解除清單寫入 `audit_logs`。
- 使用者至少要有一個所屬組織。

**理由**:自動解除會在操作者不知情時收回權限;讓操作者看著清單決定。預設選最嚴的一檔,避免留下沒有支撐的授予。

**影響**:「至少一個所屬組織」與組織刪除前置互相咬住,所以開錯的租戶走 ADR-0009「撤銷開通」,不走刪除。

## 擁有組織 = 角色的管轄邊界

**決策**:擁有組織的子樹同時回答五個問題,不另立範圍變數:

| 問題                           | 答案                                |
| ------------------------------ | ----------------------------------- |
| 誰可以被授予這個角色           | 所屬組織落在子樹內的人              |
| 移出所屬組織後還保不保這個角色 | 子樹 ∩ 剩餘所屬組織 = 空 ⟹ 失去資格 |
| 「組織外」標示                 | 持有者的所屬組織皆不在子樹內        |
| 加入使用者的選人器候選         | 所屬組織在子樹內的人                |
| 持有者在治理模組能操作哪些組織 | 子樹本身(= 管理範圍)                |

- 管理範圍 = 啟用中角色各自擁有組織子樹的聯集;持超級管理員 = 全部。
- 範圍不由持有者的所屬組織決定,也不受可見性開關影響。要給不同範圍就建不同擁有組織的角色。

**理由**:若把治理頁綁在可見範圍上,租戶管理員在開關為 `own` 時只看得到自己所屬的幾個組織,管不了自己的租戶。同一棵子樹回答五個問題,規則只有一條。

## 影響

- 登入線與殼不另開 `docs/modules/` 文件:它們不在模組樹上、沒有模組 key。帳號與 token 的規則在本 ADR;路由與側欄在 ADR-0011;密碼流程在 `docs/modules/user-manager.md`;前端分層在 ADR-0012。
- 第三方登入預留 `auth_identities`(`docs/data-model.md` 預留段),會員線開發時啟用。
