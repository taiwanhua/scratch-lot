# 權限模型:模組樹為命名空間、wildcard 同層、純加法、防越權下放

> 現況說明見 `docs/concepts/authorization.md`。

## 命名空間與 key

**決策**:

- 模組樹是權限的命名空間(模組 = 側欄 / 頁面劃分,含隱藏頁)。
- 模組 key 累加父模組 key;權限 key = 擁有模組 key + `.` + 動作。動作恆為單段,`*` 是唯一特殊動作。全小寫 kebab-case,無例外。
- key 與顯示名分離;細至欄位顯示都可以是一筆權限。

**理由**:key 一眼看得出屬於哪一頁;切分規則只有一條(最後一段 = 動作),前後端與 seed 規約測試都能機械檢查。

## 歸屬

**決策**:

- 每筆權限屬於恰好一個模組,用 `permissions.moduleId` 欄位(固定從屬用欄位,ADR-0001)。
- 綁定原則:權限綁「它作為按鈕 / 欄位 / 跳窗 / flag 所在的那一頁」;跨頁共用的綁父模組。
- 反向歸屬不解析字串:要知道權限屬於誰,看 `moduleId`;key 的前綴累加只服務可讀性。

**理由**:字串前綴會隨改名漂移;欄位是唯一真相。

## Wildcard(同層語意)

**決策**:

- 每個模組固定有一筆 `模組key.*`,由 seed 自動產生。
- `X.*` 只代表模組 X 這一層的全部權限(含未來新增),不涵蓋子模組。
- 比對只有兩種:全字串精確比對,或「擁有模組 key + `.*`」在集合中。
- 儲存:同層全給時 `role_permission` 只存 `*` 一筆;取消其中一筆時改存其餘個別筆,其他模組不受影響。
- 整組全給 = 子樹每個模組各存一筆 `*`;群組列的勾選狀態是衍生的。
- 收斂的基準必須是**全樹**,不能是裁成操作者權限集的顯示樹。
- 連動函式不可假設每個模組都有一筆 `*`:只算「餵進來的那棵樹上列得出權限」的模組。
- 解析規則:聯集、純加法、沒有 deny。
- 超級管理員例外:解析時直接全權放行;資料庫中不存在全域 `*`。

**理由**:

- 同層語意讓「全給這頁」與「全給這個子樹」分得開,子頁的權限不會被上層意外帶出去。
- 拿顯示樹收斂會擴權:操作者只看得到 5 筆、勾滿這 5 筆就被存成 `*`,而 `*` 連他沒有的那幾筆(含未來新增)一併授出。
- 顯示樹逐筆剪過權限列,可能「模組在、`*` 列不在」;照假設生出的那一筆,使用者看不到也取消不掉,送出只會被防越權擋下。
- 沒有 deny,解析永遠是一次聯集,不必處理優先順序。

## 頁面(模組)的進入權

**決策**:

- 可進 = 角色綁了那個模組(`role_module`)。route 必須明確,不可有 `*`。
- 勾下層模組必連動勾上層;有子孫被勾的上層「勾選且不可取消」。
- 隱藏頁(hidden 且有 route)key 以 `-page` 結尾;權限動作禁用 `-page` 結尾,模組 key 與權限 key 永不同字串。
- 無 route 的隱藏節點是**權限容器**(`api` 樹、根組織專屬動作的容器),不受 `-page` 規則約束。
- 隱藏頁可擁有權限,也有自己的 `*`。

**理由**:「模組 = 頁面」讓側欄、路由、權限三者共用一棵樹;樹必須完整,側欄才不會斷成孤兒。

## API 權限

**決策**:API 預設重用頁面權限 key;只有沒有對應頁面的純 API 能力,放進隱藏的 `api` 模組樹。

**理由**:避免頁面與端點雙重記帳。

## 欄位級權限

**決策**:

- 欄位級權限綁欄位所在的那一頁。讀:沒權限時 api 不把欄位放進回傳物件;寫:input 出現不能寫的欄位 → `FORBIDDEN` + `FIELD_FORBIDDEN`。
- 擋了讀,就要把繞道一起擋:**稽核歷程一律記 `[redacted]`**;清單的關鍵字搜尋不比對受保護欄位(即使操作者有讀權限)。
- 這兩條是新增欄位級權限的固定配套:投影、歷程、關鍵字三處一起改。

**理由**:「沒權限」與「沒填」在值上一樣,所以前端依權限集決定渲染。歷程會洩漏值;關鍵字比對會變成可以猜值的 oracle,而且「搜尋結果依操作者而不同」會讓分頁與 `totalCount` 對不起來。

## 防越權與稽核

**決策**:防越權分兩層,各守各的:

- **權限上限 — subset-only**:操作者只能授出自身有效權限集的子集。持有 `X.*` 可授出 X 這層任何權限與 `X.*`;子模組的 `*` 要自己持有才能授出。模組勾選同理。
- **粗篩 — 授予角色時看擁有組織**:角色的擁有組織要在操作者的管理範圍內,否則 `ROLE_OUT_OF_REACH`。超級管理員 bypass。「指派角色」與「分配使用者」是同一件事的兩個入口,判準相同。
- 操作者日後失去權限,已授出的不自動回收。
- 稽核寫 `audit_logs`(誰、何時、動作、對象、前後值),由執行動作的模組層負責;RelationService 不記。唯一例外是 `BaseRepository.reassignOrg`(搬家):租戶檢查與改歸屬都在資料層,稽核 `data.reassign-org` 也在同一個 session 由它寫(ADR-0005「例外出口」)。

**理由**:

- 若粗篩改成「只能給自己持有的角色」,自己建了角色卻不持有就永遠授不出去;兩個入口各用一套判準,會讓同一個授予從角色頁做得到、從使用者頁做不到。
- 真正的上限由 subset-only 封頂,粗篩只是讓候選清單合理。
- 稽核在模組層寫,才知道「這次操作的意圖」(例如移除組織時選了哪一檔)。

## 角色種類與可改動範圍

**決策**:三種角色,判準互斥,由上往下取第一個成立者:

| 角色種類               | 判準                   | 改名 / 描述 | 權限矩陣                           | 停用                      | 刪除       |
| ---------------------- | ---------------------- | ----------- | ---------------------------------- | ------------------------- | ---------- |
| 種子(超級管理員、模板) | `isSystem`             | 不可        | 唯讀                               | 不可                      | 不可       |
| 預設角色(租戶副本)     | `settings.templateKey` | 可          | 上限 = 模板目前的授予;租戶只能收窄 | 只有 root                 | 不可       |
| 自建角色               | 其餘                   | 可          | subset-only                        | 可,但不可停用自己正持有的 | 無授予時可 |

- 預設角色的天花板讀模板**現在**的綁定,root 也不例外;超出 → `ROLE_OUT_OF_REACH` + `TEMPLATE_CEILING`。
- 自鎖保護:不讓任何人把自己關在門外。不可逆的才禁,可逆的不禁。

**理由**:

- 種子角色隨版本更新(ADR-0002),所以唯讀而非「暫時不給改」。
- 平台要替租戶開模板沒有的模組,應先改模板(走 code + PR),而不是逐個租戶偷加。

## 影響

- 權限矩陣逐條規則與「兩棵樹」的實作在 `docs/modules/role-manager.md`。
- 欄位級權限的形狀照 `docs/agents/module-scaffold.md` 抄。
