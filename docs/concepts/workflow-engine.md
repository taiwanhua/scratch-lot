# 審核流程(現況說明)

回答「表單送出之後怎麼審」:流程誰建、怎麼綁到表單、送出時發生什麼、關卡怎麼找人、決定怎麼算、卡住了怎麼辦、誰看得到什麼。建立在表單引擎(`form-engine.md`)之上 —— 沒綁流程的提交「送出即完成」,綁了流程的表單送出後進審核,核准才完成。

api 的落地細節(寫入順序、推進執行器、決定的原子寫入、錯誤碼、稽核)在 `docs/modules/workflows.md`;前後端共用的純邏輯在 `@repo/domain/workflow`;資料表見 `docs/data-model.md`。

## 流程、版本、分派、綁定

| 部分                        | 誰建 / 誰管            | 在哪                                                               |
| --------------------------- | ---------------------- | ------------------------------------------------------------------ |
| 固定模組:申請中心、流程管理 | 開發者(seed)           | `apps/db-migrator/seeds/base/modules/apply-center.ts`、`system.ts` |
| 流程:關卡、版本             | 平台(共用)/ 租戶(客製) | 「流程管理」頁(`system.workflows`)                                 |
| 分派(共用流程 → 租戶)       | 平台                   | 業務關聯 `org_workflow`                                            |
| 綁定(租戶的表單 → 流程)     | 租戶管理員             | 業務關聯 `org_form_workflow`,在「表單管理」設                      |
| 主管(組織 → 使用者)         | 租戶管理員             | 核心關聯 `org_manager`,在「組織管理」設                            |
| 實例、任務(執行中的審核)    | 系統                   | `workflow_instances`、`workflow_tasks`                             |

- 流程可在畫面設計;明確登記的共用流程也可透過專案 seed 發布。未登記的共用流程與租戶客製流程仍由各環境獨立維護,分派、綁定與實際審核人員不隨定義搬移。受管範圍與衝突處理見[受管表單與流程](data-layer-and-isolation.md#受管表單與流程)。
- **共用流程**(`ownerOrgId = null`)給所有租戶用,審核者條件只能用權限與非指定的組織來源(見下方「審核者來源」);要用本租戶的角色、使用者或指定組織,就**以它為基底建客製流程**。租戶也可以直接建客製流程。
- 版本生命週期與表單版本**共用同一份實作**(`apps/api/src/versioning/version-lifecycle.ts`):草稿 → 發布中 → 已發布 → 已退役,四步發布、中斷可冪等重試;流程沒有欄位級權限那一步。
- **一張表單最多綁一個流程,多張表單可以綁同一個**。沒有綁定 = 不走流程,送出即完成。綁定時會先檢查「能不能直接綁」(審核者條件在共用流程能不能用、表單欄位來源對不對得上),這只是設計輔助,不取代送出時檢查。

正本:`apps/api/src/workflows/workflow-design/`、`packages/domain/src/workflow/validate-definition.ts`

## 流程結構:直線與分流 / 匯合

- **直線**:版本沒有 `edges`,`steps[]` 的順序就是流程。
- **分流 / 匯合**:一個審核關卡完成後同時啟動多條分支,各分支(一關或多關)最後接到同一個**匯合節點**(`kind: "join"`,系統節點,不派人、不能被跳過)。匯合等**全部**分支通過或依條件跳過才完成,之後可結束或接審核關卡。
- 允許的形狀:可以有多組分流,但不巢狀、不交叉、不迴圈;審核關卡入線 ≤ 1;每關在同一實例內最多執行一次。不做條件分支、迴圈、「N 條中 M 條通過」。
- **會簽模式**(關卡內幾個人要過:`any` / `all`)和匯合(跨分支、固定全部)是兩件事。
- 定義檢查器 `validateWorkflowDefinition` 前後端同一份:設計器即時跑,發布前 api 再跑,每個錯誤定位到關卡。

設計器不讓使用者自由拉線:admin 以「段落串」(主線關卡 / 一組分流)編輯,存檔時才產生 `steps` / `edges`,形狀本身就守住上面的規則;節點位置自動排版。設計器細節見 `docs/modules/workflows.md`「admin 頁面」。

正本:`packages/domain/src/workflow/graph.ts`、`validate-structure.ts`、`apps/admin/src/lib/base/workflow/flow-model.ts`

## 審核者來源

每個審核關卡選一種來源,進關時依「這張單據」算出名單:

| 來源     | 算出誰                                                                                                                                                                   |
| -------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 人員條件 | 符合條件的人:使用者 / 角色 / 所屬組織 / 權限組成的 AND / OR 樹(格式正本 `@repo/domain/audience`,與資料範圍的套用對象同一種)。例:「角色 店長 且 所屬組織 = 單據所屬組織」 |
| 表單欄位 | 該修訂的使用者引用欄選的人                                                                                                                                               |
| 主管     | 從單據所屬組織往上第 N 組主管                                                                                                                                            |

- 人員條件的所屬組織可以是指定組織,或在解析當下代入的來源:**單據所屬組織**(提交的組織)、**表單的組織欄位**(必須是組織引用欄,否則 `FIELD_NOT_ORG_REFERENCE`;送出時與綁定時同一套檢查)、**租戶**(畫面顯示「最上層組織」)。
- **共用流程只能用權限與非指定的組織來源**;用了使用者、角色或指定組織 → `AUDIENCE_IN_SHARED`(發布擋、綁定擋)。客製流程裡指定的角色與組織要屬本租戶。
- 名單只留啟用中、仍在本租戶的人;申請人本人也在名單時依這一關的「申請人也是審核者時」處理,預設剔除(見「跳過與自動通過」);一個人都沒有 → 該關「阻擋」,由流程管理者「新增審核者」。
- 列出名單(`AudienceService.listAudience`,審核者、知會、逾時通知、負責人提醒共用)時,每個條件列各自查出一群人,AND 取交集、OR 取聯集;權限條件從 `role_permission` 反推持有它的角色(含 `<模組>.*`),再找這些角色的使用者。判斷某人符不符合(資料範圍)用同一份定義,兩條路對同一組條件與使用者的結果一致(`audience.test.ts` 的表格測試)。條件只有「屬於 / 持有」、沒有「不屬於」,因為名單必須能從條件反推,不掃全部使用者。
- 解析是一個公開方法(`AudienceSourceService.resolveAudienceSource`),其他「依單據找人」的使用處直接呼叫它,不另寫一套。

正本:`packages/domain/src/workflow/approver-audience.ts`、`apps/api/src/workflows/workflow-engine/audience-source.service.ts`

## 跳過與自動通過

每個審核關卡進關時,先判斷要不要**跳過**,再派人並判斷誰**自動通過**;結果寫進實例後不再重算。

**跳過**(符合任一項就跳過,都不設 = 不跳過):

| 項目               | 怎麼判斷                                                                                                                                         |
| ------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------ |
| 申請人屬於這些組織 | 申請人送出當下的**所屬組織(全部)**有沒有在名單裡;勾「包含下層」時名單組織的下層也算。「租戶」是特殊選項(畫面顯示「最上層組織」);共用流程只能選它 |
| 符合條件           | 跳過條件公式(表單運算式),拿該修訂的值與送出當時的上下文算                                                                                        |

- 跳過的關卡是「已跳過」、沒有人核准、**不執行 `beforeApprove`**,照樣觸發 `stepPassed(skipped: true)`;時間軸記是哪一項成立(兩項都成立時記「申請人屬於指定的組織」)。
- 送出時的上下文快照多記了**租戶**與**所屬組織(全部)**,公式也能用:`ctx.tenant.id`、`ctx.user.orgIds`(`ctx.user.orgId` 是目前組織)。

**申請人也是這一關的審核者時**(每關三選一,預設「剔除申請人」;解析出的名單含申請人本人才有作用):

| 設定             | 行為                                                                                                                                                                   |
| ---------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 剔除申請人(預設) | 名單去掉申請人,其他審核者照常審;只剩申請人 → 該關阻擋,由流程管理者新增審核者                                                                                           |
| 自動通過         | 記成申請人的核准(過了 `beforeApprove` 才算);被擋下 → 照「剔除申請人」                                                                                                  |
| 照常審核         | 申請人留在名單,和其他審核者一樣拿一張待審任務(寄「有新任務」、在「待我審核」),自己再按一次核准 / 駁回 / 退回;核准照樣經 `beforeApprove`。只剩申請人也不阻擋,任務派給他 |

**審核者已在前面的關卡核准過**(兩選一,預設「照常審核」):自動通過 = 記成他的核准。只看**這一輪**(最近一次送出之後)、這一關上游的關卡、記在他名下的有效核准;退回後重送從頭算。

- 自動通過 = 那個人的一票:會簽 `all` 只算他那一票,其他人照常審;`any` 一票就過。照常審核的申請人也是一票:`any` 任一人(含申請人)核准就過、其他人的任務取消;`all` 申請人與其他人都要核准。
- **自動通過照樣執行 `beforeApprove`**(以那個人的身分,進關時先跑再派任)。被擋下時:申請人回到這一關的「申請人也是審核者時」—— 剔除申請人 / 自動通過 → 剔除(其他審核者照常審;剔除後沒人 → 阻擋);照常審核 → 留著一張待審任務;其他人照常留一張待審任務。時間軸記「申請人自動通過未成立 / 已在前關核准,自動通過未成立」與專案的文案。
- 照常審核和「已在前面的關卡核准過」可以一起開:申請人前關核准過 → 這一關自動記上他那一票;守門擋下 → 他照常審。
- 時間軸記「申請人是審核者,自動通過」/「已在前關核准,自動通過」;照常審核時申請人自己按的核准和一般審核者一樣記。代理人代為核准的票記在代理人名下,只算代理人。
- **只作用在解析出的名單**:主管來源本來就從提交所屬組織往上找、不含申請人本人(主管 = 申請人的主管,見下方「實例是唯一權威」),三個設定都不改主管的解析。
- **改派與新增審核者**(阻擋清單)指定給申請人:只有這一關設「照常審核」才可以(他之後照常審自己的單);剔除申請人與自動通過 → 不能選申請人(`ASSIGNEE_NOT_ELIGIBLE`)。看的是那個任務 / 關卡在版本定義裡的設定,與進關同一個判準。

正本:`packages/domain/src/workflow/plan.ts`(`isApplicantInSkipOrgs`、`applicantAsReviewerOf`、`autoApprovalCandidates`)、`advance.ts`(列 5)、`apps/api/src/workflows/workflow-engine/step-entry.service.ts`

## 代理人

每個人可以在個人設定的「代理人」分頁設定自己的代理(誰、從哪天到哪天);只能設定自己的,所有登入者都能用(個人設定不分配給角色)。代理期間內**進關**派任時,輪到他的任務改派給代理人:

| 情況                                | 結果                                                                         |
| ----------------------------------- | ---------------------------------------------------------------------------- |
| 審核者在代理期間                    | 任務派給代理人;派任計畫記原審核者與代理人                                    |
| 代理人停用 / 不在本租戶             | 照原審核者派任,記 log                                                        |
| 代理人是申請人                      | 這張單的任務留在原審核者名下(不自己審自己)                                   |
| 原審核者是申請人                    | 不改派(依這一關的設定剔除、自動通過,或由申請人自己照常審核)                  |
| 代理人自己也在代理期間              | 仍派給代理人,不往下傳(不做代理鏈)                                            |
| 代理開始前已派出的任務;代理刪除之後 | 不動(計畫固定);需要時由流程管理者「改派」                                    |
| 會簽多位審核者委託同一位代理人      | 代理人一張待辦、一票,一次核准 / 退回作用到所有被代理者(引擎仍是一人一關一票) |
| 代理人本人原本就在名單              | 仍是他自己的一張待辦,另記他代理的人                                          |
| 流程管理者改派給正在代理期間的人    | 任務與通知給被選的人,不轉給他的代理人(代理只在進關派任時套用)                |

- 改派發生在解析審核者之後、自動通過之前,所以「已在前關核准過」只算代理人本人(代理人前關核准過、這一關又輪到他代理 → 自動通過;原審核者不算核准過)。
- 時間軸:派任寫「由 王小明 代理 李店長」,代理人的核准 / 駁回 / 退回寫「由 王小明 代理 李店長 核准」(多位被代理者全列);關卡進度寫「王小明(代理 李店長)」。流程管理者改派後不再記被代理者。
- 不提供改結束日:提早結束 = 刪除這筆代理,延長 = 刪除後重新設定。
- 代理人是任務持有者,照「任務持有者」規則讀得到他審的修訂;「有新任務」通知給代理人。
- 起訖是時點:依租戶時區選日期,起 = 當天 00:00、迄 = 結束日 24:00(不含)。同一個人的代理期間不重疊;已結束的唯讀、保留紀錄。

正本:`apps/api/src/workflows/workflow-engine/assignee-delegation.service.ts`、`apps/api/src/user-delegations/`、`packages/domain/src/workflow/plan.ts`(`buildPlan` 的 `delegatorOf`)

## 逾時提醒與知會

**逾時提醒**:每個審核關卡可以設「超過 N 小時未處理 → 通知審核者;超過 M 小時 → 同時通知通知對象」(預設關閉;M 要大於 N:設計器擋下不讓存;api 存草稿照收、在檢查結果回 `OVERDUE_INVALID`,發布擋下)。通知對象是人員條件,預設為持有阻擋清單改派權限的人(流程管理者)。**只提醒,不自動核准或駁回**。

| 情況                   | 結果                                          |
| ---------------------- | --------------------------------------------- |
| 任務超過 N 小時未處理  | 通知目前的審核者一次                          |
| 任務超過 M 小時未處理  | 通知「通知對象」一次;審核者不再重複收到       |
| 任務改派               | 新的承辦人重新計時                            |
| 代理人承接的任務超過 N | 代理人與每位被代理者都收到                    |
| 代理人承接的任務超過 M | 通知對象收到(剔除代理人;被代理者在名單內照收) |
| 代理承接的任務被改派   | 只提醒新的承辦人                              |
| 任務在排程跑之前已處理 | 不通知                                        |
| 夜間、假日             | 照算(日曆小時,從任務派給目前承辦人時起算)     |
| 這一關沒有開啟         | 不檢查、不通知                                |

排程每 15 分鐘檢查一次(排程任務的工作 `workflow.overdue-reminders`),通知類型 `workflow.overdue`(站內、email)。

**知會**:每個審核關卡或整個流程可以設知會對象,來源同審核者三種(人員條件 / 表單欄位 / 主管),依這張單據算人;知會對象不用審核。

| 情況                                        | 誰收到知會                         |
| ------------------------------------------- | ---------------------------------- |
| 設定了知會的關卡整關通過                    | 該關的知會對象                     |
| 設定了知會的關卡被跳過                      | 該關的知會對象                     |
| 單據完成                                    | 整個流程的知會對象                 |
| 單據被駁回                                  | 整個流程的知會對象                 |
| 單據被作廢                                  | 整個流程的知會對象                 |
| 只設在關卡的知會對象,單據完成 / 駁回 / 作廢 | 不收(要收就加進整個流程的知會對象) |

單據層的結果只給整個流程的知會對象,關卡的知會對象不收;想讓某人也知道最後結果,就把他加進整個流程的知會對象。退回後重送是新實例、從第一關重審,再通過該關時關卡知會對象會再收到一次。

- 通知類型 `workflow.cc`(站內),內容寫是哪個時機(「「主管審核」關卡已通過」「已完成」…),連結到申請中心詳情頁。退回、撤回不知會。
- 知會和觸發它的動作在**同一個交易**:動作回復就沒有知會通知,也讀不到。
- 收過知會的人以「任務持有者」同等規則**唯讀**被知會的那個修訂(提交內容、實例歷程、附件),不能做任何操作;他不是任務持有者,「待我審核」裡沒有這張。
- 知會對象、逾時的通知對象在送出、綁定時不檢查、不擋;執行時算不到人(表單欄位沒填、條件沒人符合、欄位來源指向別張表單…)就不發,並記 warn log 寫明原因。不剔除申請人。

正本:`apps/api/src/workflows/workflow-engine/workflow-overdue.service.ts`、`workflow-cc.service.ts`、`packages/domain/src/workflow/types.ts`(`OverdueReminderDef`、`ReviewStepDef.cc`、`WorkflowDefinition.cc`)

## 送出:從提交到實例

每次送出(含退回 / 撤回後再送出)都先做**送出時檢查**:這筆提交綁的**表單版本** + 現在綁的流程**目前發布版**搭不搭。會擋下的情況:

| 情況                                                                                                                                                                                                                  | 申請人看到                          |
| --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------- |
| 審核者的表單欄位來源指向別張表單(`FORM_MISMATCH`),或欄位在這個表單版本不存在(`FIELD_MISSING`)、不是使用者引用欄(`FIELD_NOT_USER_REFERENCE`);人員條件用的表單組織欄位不存在或不是組織引用欄(`FIELD_NOT_ORG_REFERENCE`) | 流程設定有誤,請聯絡管理員           |
| 跳過條件引用的欄位在這個表單版本不存在(`UNKNOWN_FIELD`)、是受保護欄位(`PROTECTED_FIELD`),或條件本身不合法(`INVALID_EXPRESSION`)                                                                                       | 流程設定有誤,請聯絡管理員           |
| 綁的流程沒有發布版                                                                                                                                                                                                    | 流程尚未發布                        |
| 進過審核的單,綁定被解除或流程被收回;或綁定指向被收回 / 不存在的流程                                                                                                                                                   | 此表單的審核流程已移除,請聯絡管理員 |

失效的綁定一律擋,不會默默免審。沒進過審核、現在也沒綁 → 照沒綁流程的方式送出。

檢查通過後還要過修訂數與文件大小的上限,見 `docs/modules/forms.md`「提交的寫入規則」。

通過後**在一個交易裡**依序:建實例(從起點開始)→ 提交同一次更新成「審核中」並連上實例 → 推進(連同稽核)。任一步失敗整個送出回復(實例、任務都不存在,提交維持送出前),重送就是重新送一次;不會多一個實例、也不會多一個修訂號。已在審核中再送一次 = 對原實例再推進一次。**送審不經過「已完成」**。

實例記 `(workflowKey, workflowVersion)` 與該修訂的摘要快照;之後流程改版、退役、收回分派、表單停用都**不影響進行中的實例**,只影響新送出。

正本:`apps/api/src/workflows/workflow-engine/workflow-submit.service.ts`、`packages/domain/src/workflow/submit-check.ts`

## 實例是唯一權威

| 放在實例上(權威)                                                     | 投影 / 衍生                              |
| -------------------------------------------------------------------- | ---------------------------------------- |
| 進行中的關卡(平行時多個)、每關狀態、派任計畫、被接受的決定、終局結果 | 審核任務(`workflow_tasks`)的狀態與承辦人 |
| 歷程(時間軸)                                                         | 提交的狀態與「待處理」標記               |

- **推進**(`advance`)是引擎唯一會改關卡與任務的動作:讀實例與全部任務 → 依判斷表找出該做的事(建任務、關卡完成、啟動後繼、匯合、終局、收尾、解除阻擋)→ 每個寫入都是條件更新 → 重讀再判斷,直到沒事可做。整段推進與觸發它的動作在同一個交易裡;任何入口重跑結果相同。判斷表是純函式(`advance.ts`),不碰資料庫。
- **審核者只在進關時解析一次**,寫進派任計畫後不重算:條件後來多符合了人不補任務;不再符合條件(例如角色被拿掉)的人仍可審;人被停用或移出租戶走「阻擋」。
- **主管**:從**提交所屬組織**往上找第一組主管(第 2 層再往上一組),上界是提交的租戶頂層;申請人自己剔除,剔除後為空就再往上。
- **決定**記進實例才算被接受,接受與其後的推進在同一個交易裡。兩人同時決定同一份實例:先提交的那筆算數,後到的交易寫入衝突、整個重跑,重讀後依當下狀態判 —— 關卡已結束就回「此關已結束」(不是錯誤),關卡仍進行中(如會簽的另一位、另一條平行分支)就照常接受。接受條件見 `docs/modules/workflows.md`「決定、撤回、改派、新增審核者、審核者失效」。
- **終局**:任一關卡(含任一分支)有效駁回 / 退回 → 全案終局,其他分支沒決定的任務取消、已做的決定保留;全部走完且終點完成 → 核准,提交「已完成」並**鎖定**(只能作廢)。

正本:`packages/domain/src/workflow/advance.ts`、`evaluate.ts`、`projection.ts`、`apps/api/src/workflows/workflow-engine/`

## 提交的七個狀態

| 狀態   | 意思                                        | 申請人能做                    |
| ------ | ------------------------------------------- | ----------------------------- |
| 草稿   | 存了沒送                                    | 改、送、刪                    |
| 審核中 | 有進行中的實例(被阻擋時標「待處理」)        | 還沒人審過前可撤回            |
| 已退回 | 被退回修改                                  | 改完再送(修訂 +1、重新審)、刪 |
| 已撤回 | 申請人自己收回                              | 同已退回                      |
| 已完成 | 沒走流程:送出即此,可再改;走過流程:核准,鎖定 | 走過流程的只能作廢            |
| 已駁回 | 審核駁回,不能再改、不能再送                 | 另開一張                      |
| 已作廢 | 核准後作廢(不需審核),內容凍結               | 複製為新單                    |

走過流程的提交不參與「舊版資料升級」,綁了流程的表單也不能升級(`docs/modules/forms.md`「舊版資料升級」)。

正本:`packages/domain/src/workflow/types.ts`、`docs/modules/workflows.md`「狀態機」

## 卡住了:阻擋、改派、重試推進

- **阻擋**:關卡解析不到有效審核者,或承辦人失效(停用 / 移出租戶,包括使用者管理的「複製組織與角色」取代模式移除組織),就停住等人處理 —— **不自動改派、不自動跳過**。其他分支照常審,匯合等它解除。
- 流程管理者在「流程管理 → 阻擋清單」處理(權限 `system.workflows.blocked-page.reassign`):**改派**(換承辦人,原承辦人記為曾持有)、**新增審核者**(只給解析為空的關卡)、**重試推進**。
- 「需要推進」篩選列的是還有事可做的實例(判斷表 dry-run 的結果;動作都是交易,正常不會留下,出現代表舊資料或資料被改過);候選太多時只檢查最久沒動的一批並提示。

正本:`apps/api/src/workflows/workflow-engine/blocked-instances.service.ts`、`assignee-invalidation.service.ts`

## 申請中心與誰看得到什麼

- **申請中心**(`apply-center`)是固定模組,兩個**跨模組**頁籤,依序是「我的申請」(我送的、走過流程或表單綁了流程的,預設頁籤)與「待我審核」(派給我的任務);右上「新申請」選模組 → 選表單 → 進該模組的新增頁。表單都留在各自的業務模組。
- 兩個頁籤與側欄都有待辦數字 badge,條件與顯示規則見 `docs/modules/workflows.md`「計數」。
- 申請中心有自己的隱藏詳情頁(通知信的連結也是它),**不經業務模組的頁面權限**:沒有該模組權限的審核者也看得到他要審的那一張。
- 誰讀得到提交只有一份判準(`canReadSubmissionRevision`):模組讀者照一般規則,申請人讀得到自己的單,審核者**只讀得到他審的那個修訂**,流程管理者在阻擋清單只看標題。細節見 `docs/modules/workflows.md`「讀取授權」。
- 任務清單、通知信、詳情的摘要一律讀**實例上的快照**,不讀提交最新的摘要 —— 否則只審過前一個修訂的人會看到新修訂的標題。

## 掛接點:守門與事後動作

專案可以在表單 / 流程的時間點檢查與寫入自己的資料(收貨入庫、數量鎖定、記帳),**都在動作的同一個交易內**。登記在固定入口 `apps/api/src/project/form-lifecycles.ts`(`registerFormLifecycle({ moduleKey, formKey?, inject, guards, effects })` 的靜態清單,`formKey` 省略 = 整個模組),由 `database/database.module.ts` 組裝;同一個 (moduleKey, formKey) 重複、同一個模組同時登記整個模組與指定表單、`formKey` 為 `"*"`、名字不認得 → api 與受管定義 CLI 起不來。`inject` 列 handler 要用的 provider token,api 啟動時逐一解析(找不到 → 起不來);因為這個檔在資料層組裝時就載入,列的 class 不能(直接或間接)import `database.module.ts`,否則是循環 import,組裝時報「inject 有空的 token」。

**守門**(8 個):寫入之前呼叫、只能讀,回 `null` = 通過、回 `{ code, message }` = 擋下 → `FORBIDDEN` + `reason` = 專案錯誤碼(大寫英數與底線),這個動作沒有任何寫入;前端(`apps/admin/src/lib/base/errors.ts` 的 `adminErrorText`)把這種認不得的 reason 對到專案字典 `admin.lifecycle.<錯誤碼>`(專案在 `admin.json` 加 `lifecycle` namespace),沒有這個 key 就顯示通用的「沒有權限」。收到:操作者(按下按鈕的人)、提交、這一版的值、關卡、`session`、`get`(只拿得到登記時 `inject` 宣告的 provider)。

| 守門                  | 時機                                                  | 這一版的值 / 關卡 |
| --------------------- | ----------------------------------------------------- | ----------------- |
| `beforeSubmit`        | 驗證與送出時檢查之後、寫入之前(含退回 / 撤回後再送出) | 這次要寫入的值    |
| `beforeApprove`       | 核准;一律經 `FormLifecycleService.runApproveGuard`    | 關卡 key          |
| `beforeReject`        | 駁回                                                  | 關卡 key          |
| `beforeReturn`        | 退回                                                  | 關卡 key          |
| `beforeWithdraw`      | 申請人撤回                                            | —                 |
| `beforeVoid`          | 作廢(context 另帶 `voidReason`)                       | —                 |
| `beforeDelete`        | 刪除(草稿 / 被退回 / 撤回、沒走流程的已完成、已駁回)  | —                 |
| `beforeEditCompleted` | 修改沒走流程的已完成單                                | 新的值            |

**事後動作**(7 個):狀態改變後在同一個交易內呼叫;拋錯 = 整個動作(狀態、任務、實例、專案寫入)回復。收到:事件、提交 id、修訂號、關卡、`skipped`、`session`、`get`、`notify()`(通知的單一入口 `NotificationService.notify()`,寫入併進這個動作的交易;見 `docs/modules/notification-settings.md`)、`realtime.publishAfterCommit()`(提交後才送),以及**系統身分**的操作者:沒有操作者與角色,可見範圍 = 單據的組織(租戶頂層開了「含下層」時含其下層),不使用按下按鈕那個人的權限。另帶 `actorId` = 造成這個事件的人(`submitted` 送出的人(沒走流程直接完成時接著的 `completed` 也是)、`voided` 作廢的人、`rejected` / `returned` 做這個決定的審核者;其他事件與沒有登入主體的動作為 null),只用來記「誰讓資料變了」(例:基礎欄位的修改者),不是權限來源。

| 事件         | 觸發點                                                                                       |
| ------------ | -------------------------------------------------------------------------------------------- |
| `submitted`  | 送出建好實例、提交進審核中之後(推進之前);沒走流程的單直接完成時先 `submitted` 再 `completed` |
| `stepPassed` | 推進把審核關卡改成完成 / 跳過(跳過帶 `skipped: true`;匯合節點不觸發)                         |
| `returned`   | 推進把提交同步成被退回(關卡 = 做決定的那一關)                                                |
| `withdrawn`  | 推進把提交同步成已撤回                                                                       |
| `completed`  | 推進把提交同步成已完成;或沒走流程的送出                                                      |
| `rejected`   | 推進把提交同步成已駁回(關卡 = 做決定的那一關)                                                |
| `voided`     | 作廢寫入之後(context 另帶 `voidReason`)                                                      |

作廢的守門與事後動作另帶 `voidReason: { reasonKey, reasonLabel, reasonNote }`(表單沒設作廢原因類別時 `reasonKey` / `reasonLabel` 為 null、`reasonNote` 是自由文字理由;見 `docs/modules/forms.md`「作廢原因」)。

推進裡的事件只在條件更新真的命中時觸發;推進可由別的動作帶動(重試推進、審核者失效),事後動作就跟著那個動作的交易;失效 hook 觸發的事後動作失敗時,停用照樣生效(hook 在停用寫入之後、各實例自己的交易),該實例要再停用一次才會補做。

正本:`apps/api/src/workflows/workflow-engine/lifecycle/`、`apps/api/src/project/form-lifecycles.ts`

## 一個動作一個交易

送出、決定(核准 / 駁回 / 退回)、撤回、作廢、改派、新增審核者、重試推進、審核者失效(每個實例)各是一個 Mongo 交易(ADR-0013),推進(含連續推進)併在觸發它的動作裡:任一步失敗,這個動作的所有寫入一起回復。並發的兩個動作寫到同一份實例 → 後到的寫入衝突、整個交易重跑,重讀後再判斷。實例上的條件更新(`editVersion` 等)照舊保留,判斷表也照舊冪等。「重試推進」與阻擋清單保留:阻擋是業務狀態(找不到審核者),不是一致性補救。

正本:`docs/modules/workflows.md`「推進」「通知信」、`docs/adr/0013-mongo-transactions.md`

## 通知

流程的通知走通知的單一入口 `notify()`(`docs/modules/notification-settings.md`),站內通知與 email 由同一個入口產生:

- **任務建立** → `workflow.task-created` 給該任務的審核者;**改派** → 同一類型給改派後的承辦人(原承辦人不另外通知;改派回已收過的人不重複);**有結果**(核准 / 駁回 / 退回)→ `workflow.result` 給申請人,駁回 / 退回附理由。兩種都是當事人通知,連結到申請中心詳情頁(連結種類 `workflow-instance`)。
- **與推進同一個交易**:通知寫進推進的交易,交易回復(含被自動重試丟掉的那一輪)就沒有通知、沒有信號、沒有信;站內的 `notification` 信號與 email 在交易提交後才送。
- **不重複**:`dedupeKey` = 類型 + 實例 + 任務 / 結果,同一位收件人只會有一則;實例歷程的 `task_created` / `notified` 標記讓重試推進不再觸發。`task_created` 以「任務 + 承辦人」為單位(改派不換任務,新承辦人沒有自己的標記才補通知)。
- **盡力通知**:email 依收件人的個人偏好(審核者的站內通知不能關)與總開關 `WORKFLOW_MAIL_ENABLED`;寄信失敗只記 log、不影響推進。
- 內容只讀實例快照(表單名、實例上的標題槽、關卡名)。

正本:`apps/api/src/workflows/workflow-engine/workflow-notifier.service.ts`、`apps/api/src/notifications/notification.service.ts`
