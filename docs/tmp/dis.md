### 人員條件權限選項:root 看得到租戶客製表單的模組權限

`audiencePermissionOptions`(人員條件的權限樹)沿用權限矩陣的顯示樹與 `foreignFieldPermissionKeys` 過濾:只擋別租戶客製表單的**欄位級**權限(`show-` / `edit-`)。root 是超級管理員,有效權限集是全部,所以租戶客製表單**模組本身**的權限(`<表單模組>.view` 等)仍會出現在 root 的樹裡,與規格「資料範圍由 root 設定,只列底座與專案的權限」有落差。權限選項的過濾規則待 B12 定案,畫面端在 #38(T23)。

現況:未開票;T06 依 Spec #15 決定沿用現有過濾,不等 B12。

### 人員條件的角色 / 使用者候選:一次 100 筆、借清單權限

AudiencePicker 的角色、使用者候選(`useAudienceOptions`)借 `roles` / `users` 清單查詢,一次取 100 筆、只在前端篩選;要有 `system.role-manager.view` / `system.user-manager.view` 才查得到,沒有就是空清單。root 站在根組織時看得到全部租戶,角色與使用者很容易超過 100 筆,候選會缺漏(已存的值不在清單裡時顯示「不在候選清單中」、仍保留)。#45(T30)流程審核者 / 知會、#55(T40)通知設定等租戶端的使用處接上 AudiencePicker 後也會遇到同樣問題,而那些操作者不一定有這兩個檢視權限。可能做法:改成伺服器端搜尋(關鍵字丟回 api、專給人員條件的候選查詢,不借角色 / 使用者管理的權限)。

現況:未開票;#38(T23)審查時記下,本票維持現況。

### 改派 / 新增審核者與使用者停用同時發生

改派、新增審核者在交易內讀「使用者仍啟用」是快照讀;若「停用該使用者」恰好在讀完資格、寫入之前提交,而停用不會寫到同一份流程實例,交易抓不到這個衝突,結果剛停用的人仍被派任。停用的失效 hook 抓候選實例時也看不到這筆。發生時要等下一次異動或再停用一次才補做失效。可能做法:提交後對新指派者再跑一次失效檢查,或停用時對該使用者的候選實例加鎖。

現況:未開票;#36(T21)審查時記下,機率極低(兩個動作要在同一瞬間發生),本輪不處理。
