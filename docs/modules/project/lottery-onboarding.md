# 租戶開通清單(刮刮樂 + 排班與出勤)

一家新的刮刮樂公司開始用系統前要設定好的事,以及做這些事的三樣工具。漏了任何一步系統都會出狀況(例:沒有審核流程,單據送不出去)。本檔是正本:開通 skill 照它問、開通腳本照它做、示範指令灌的示範資料走同一套步驟。

| 工具       | 位置                                                                                         | 做什麼                                                                                                                                     |
| ---------- | -------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------ |
| 開通 skill | `.claude/skills/scratch-lot-onboarding/`(`.agents/skills/` 同名)                             | 讀本檔 → 問新租戶的資料 → 寫成開通資料檔 → 請操作者在**自己的終端機**跑開通腳本(skill 不經手密碼)→ 人工步驟列成清單                        |
| 開通腳本   | `apps/db-migrator/seeds/project/onboarding/`(指令 `onboard`)                                 | 以租戶管理員登入,呼叫既有的 GraphQL 做完下表標「自動」的步驟;權限照常檢查、操作紀錄記在這位管理員名下;不連資料庫                           |
| 示範指令   | `pnpm --filter @repo/db-migrator demo …`(底座機制,見 `docs/deployment.md`「示範資料(demo)」) | 平台管理員建立標「示範」的機構與首任租戶管理員,再把 `apps/db-migrator/seeds/project/demo/` 的示範資料交給**同一支開通腳本**;三個環境都能跑 |

## 開通步驟

前提:平台管理員已在組織管理「開通租戶」建好租戶與首任租戶管理員,那位管理員已用啟用信設好密碼。

| #   | 項目                                  | 做什麼、為什麼                                                                                                                                                                             | 在哪個畫面           | 開通腳本                                                                                       |
| --- | ------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | -------------------- | ---------------------------------------------------------------------------------------------- |
| 1   | 組織可見性                            | 租戶的可見性開關設為「包含下層」(不改底座預設值,只改這個租戶):總部人員與店長才看得到下層分店的資料                                                                                         | 組織管理             | 自動                                                                                           |
| —   | 分店                                  | 依開通資料建立分店(最上層組織的直接下層);已有同名的沿用                                                                                                                                    | 組織管理             | 自動                                                                                           |
| 2   | 使用者與總部人員的所屬                | 依開通資料建立使用者並給所屬分店與角色;**總部人員一律同時加入最上層組織**,總部若是某家分店也加入那家店。新建的人收到啟用信自己設定密碼;已存在的帳號只補缺的所屬與角色,密碼與基本資料不動   | 使用者管理           | 自動                                                                                           |
| 3   | 租戶管理員模板用 `*` 授予整層         | 專案 seed 一次做好(不是逐租戶):模板逐條列權限的話,動態權限(B9b)不會出現在租戶管理員身上                                                                                                    | 角色模板(專案 seed)  | —                                                                                              |
| 4   | 開通時建立的角色:總部管理、店長、店員 | 三個一般角色(和租戶自己建的沒有差別,畫面沒有「預設角色」標籤);權限配方見下方「角色配方」。只對新建的角色套配方:已有同名角色、而且有任何權限的不覆蓋                                        | 角色管理             | 自動                                                                                           |

| 6   | 乙類與對應分店;銀行帳戶與使用組織     | 建立乙類並對應分店(開通資料的 `classBDealers`,以證號找回、已存在不動);建立銀行帳戶並設定使用組織                                                                                           | 經銷商管理、帳戶管理 | 乙類:自動;銀行帳戶:人工(帳戶管理 → 新增帳戶)                                                   |

| 8   | 叫貨單的 B4 跳過組織                  | 預設「租戶」;總部是某家分店時改選那家分店                                                                                                                                                  | 流程設定             | 自動(建叫貨單流程時一起設;開通資料的 `headquartersBranch`)                                     |

| 10  | 經銷商的兩個批購基準日                | 上線前最後一次批購的日期,匯入或手動填寫                                                                                                                                                    | 經銷商管理           | 人工                                                                                           |
| 11  | 排班                                  | 確認排班規則總部預設值、加入排班人員(可以排的分店、主要分店、僱用類型)、建立人力需求範本與週範本                                                                                           | 班表管理             | 加入排班人員、人力需求範本:自動(開通資料有列才建);規則:人工確認                                |
| 12  | 通知的收件人與提醒時間                | 規格 3.4 預設收件人是「角色 店長」的四種負責人提醒(日結逾期、調貨出貨通知、證照到期、牌租繳費提醒),開通腳本建好角色後把收件人改成角色 店長;其餘類型與提醒時間照預設,需要時在通知設定頁調整 | 通知設定             | 四種收件人:自動;其餘人工確認                                                                   |

- 第 12 點的四種通知在類型宣告的預設收件人是「持有 `store.bank-deposit`」(角色 id 每個租戶不同,寫不進宣告)。開通腳本只改**還是預設值**的;租戶已調整過的不動。租戶若在通知設定頁「還原預設」,之後重跑開通腳本會再改成角色 店長(還原後就是預設值,分辨不出來)。**沒走開通腳本的租戶**,收件人停在權限預設,要自己到通知設定頁改成角色 店長。
- 每一步冪等:已經有的沿用,不改回去。某一步失敗(例:租戶管理員沒有那個權限)→ 照 api 回的錯誤停在那一步並列出未執行的步驟,已完成的保留;補好之後重跑,從缺的開始補。

## 執行開通腳本

開通資料是一個 JSON 檔(形狀見 `apps/db-migrator/seeds/project/onboarding/plan.ts`),**不放任何密碼**(出現名稱含 password 的欄位就拒絕),也不進 repo:

```json
{
  "branches": [{ "name": "中山店" }, { "name": "信義店" }],
  "headquartersBranch": null,
  "users": [
    {
      "account": "hq@example.com",
      "email": "hq@example.com",
      "name": "總部人員",
      "branches": [],
      "headquarters": true,
      "roles": ["hq"]
    },
    {
      "account": "manager@example.com",
      "email": "manager@example.com",
      "name": "中山店店長",
      "branches": ["中山店"],
      "headquarters": false,
      "roles": ["store-manager"]
    }
  ],
  "positions": [
    { "value": "in-store-counter", "label": "店內櫃台", "color": "blue" }
  ],
  "cashPoints": [
    {
      "branch": "中山店",
      "positionKey": "in-store-counter",
      "name": "店內櫃台",
      "order": 1
    }
  ],
  "scheduleStaff": [
    {
      "account": "manager@example.com",
      "employmentType": "full-time",
      "branches": [{ "name": "中山店", "canLead": true, "isPrimary": true }]
    }
  ],
  "scheduleTemplates": [],
  "scheduleWeekTemplates": []
}
```

- `scheduleStaff`(選填):加入排班的人,`account` 要在 `users` 內;`employmentType` = `full-time` 正職 / `part-time` 兼職;`branches` = 可以排的分店(`canLead` 可擔任負責人、`isPrimary` 主要分店,恰好一家)。只在這個人還沒設定任何分店時寫入,已設定的不動。
- `scheduleTemplates` / `scheduleWeekTemplates`(選填):最上層組織的人力需求範本(`name`、`shortName` 1–2 字、`startTime` / `endTime` `HH:mm`、`positionKey` 崗位代碼、`tasks` = `{ role: leader / helper, taskKey }`、選填 `color`)與週範本(`days` 7 格,0 = 星期日,每格是範本名稱);以名稱找回,已存在的不動。
- `roles`:`hq` = 總部管理、`store-manager` = 店長、`clerk` = 店員。
- `headquartersBranch`:總部是某家分店時填那家店的名稱;總部就是租戶本身時為 `null`。
- `positions`:這個機構的崗位(`value` 英文 kebab-case、`label` 顯示名稱、選填 `color` = 標籤色票代號 `blue` / `cyan` / `green` / `lime` / `yellow` / `orange` / `red` / `pink` / `purple` / `grey`)。**專案 seed 不內建任何崗位**,收銀點與人力需求範本用到的崗位都要列在這裡(或開通前已在欄位管理建好);沒有就空清單(之後在欄位管理建)。建成這個租戶自己的選項;顏色只在選項還沒有顏色時設定,租戶已選過的不動。
- `cashPoints`:開通時建立的收銀點(`branch` 分店名稱、`positionKey` 崗位選項值 —— `positions` 裡的(或這個租戶已有的)、`name`、選填 `order`);以「分店 + 崗位」找回,已存在的不改;印表機不設(用分店預設)。沒有就空清單。

在**自己的終端機**執行(租戶管理員密碼在終端機輸入、不回顯;不從參數、環境變數或檔案讀):

```bash
pnpm --filter @repo/db-migrator onboard --api-url=<該環境的 api 網址> --tenant=<租戶短碼> --account=<租戶管理員帳號> --plan=<開通資料檔>
```

`--api-url` 是該環境的 api origin(`deploy/project/cloud.json` 各環境的 `apiUrl`,例 `https://api-dev.scratch-lot.com`)。`--tenant` 是要開通的租戶短碼(開通租戶時填的):登入者所屬的租戶不是它,就停在第一步,一筆都不寫。

## 表單代號與流程

formKey 組成動態權限 `<模組>.create-<formKey>`(只有開啟 B9b 的 `store` 有),也是流程綁定用的代號;使用者畫面只看到中文名稱。審核者寫法:「店長限定 X」= 人員條件「角色 店長 且 所屬組織屬於 X(本身)」。

| 表單         | formKey             | 綁定模組                 | 開通時建立的流程                                                                                                                                                                                              | 開通腳本 |
| ------------ | ------------------- | ------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------- |
| 撤銷售出申請 | `sale_reversal`     | `store`                  | 一關:店長限定「分店」;B5 申請人是審核者時自動通過                                                                                                                                                             | 自動     |
| 現金更正單   | `cash_correction`   | `store`                  | 一關:店長限定「分店」;B5                                                                                                                                                                                      | 自動     |
| 盤點確認申請 | `stocktake_confirm` | `store`                  | 一關:店長限定「分店」;B5 申請人是審核者時自動通過                                                                                                                                                             | 自動     |
| 結帳確認申請 | `checkout_confirm`  | `store`                  | 兩關:第 1 關「接班人確認」審核者 = 欄位「接班人」,跳過條件 類型 = 日結或接班人為空;第 2 關「店長審核」店長限定「分店」,跳過條件 類型 = 交班且接班人不為空(底座的跳過條件運算式),B5 申請人也是審核者時照常審核 | 自動     |
| 叫貨單       | `requisition`       | `purchasing.requisition` | 一關:角色 總部管理;B4 跳過組織 = 租戶(總部是分店時改選那家店);B5 申請人也是審核者時照常審核                                                                                                                   | 自動     |
| 進貨單       | `purchase`          | `purchasing.purchase`    | 一關「點收」:店長限定「進貨分店」;B5 申請人也是審核者時照常審核                                                                                                                                               | 自動     |
| 調貨單       | `transfer`          | `purchasing.transfer`    | 兩關:第 1 關「出貨確認」店長限定「出貨分店」,跳過條件 `ctx.user.orgId == 出貨分店`;第 2 關「點收」店長限定「收貨分店」;兩關都 B5 申請人也是審核者時照常審核                                                   | 自動     |
| 補打卡申請   | `makeup_punch`      | `schedule.attendance`    | 一關:店長限定「分店」;B5 申請人也是審核者時照常審核                                                                                                                                                           | 自動     |
| 支援需求單   | `support_request`   | `schedule.manage`        | 一關:人員條件「角色 總部管理 且 所屬組織屬於租戶(最上層組織本身)」;B5 申請人也是審核者時照常審核                                                                                                              | 自動     |

- 開通腳本的「流程」一步(`onboarding/steps/form-workflows.ts`)逐張表單:表單還沒分派給這個租戶 → 略過並提示「平台管理員在表單管理分派後重跑」;表單已綁了流程 → 沿用(租戶自己換過的不改回去);否則建立租戶客製流程(key `<租戶短碼>_<formKey>`,全域唯一)、存定義、發布、綁定表單。流程已存在但還沒發布(上次中斷)→ 接續草稿發布。
- 受管表單由部署發布成共用表單(`seeds/project/revisions/`),**分派給租戶**仍是平台管理員在表單管理做的(開通腳本以租戶管理員登入,做不到);示範指令 `demo create` 由平台管理員建完示範機構後,在同一個平台管理員 session 把 registry 登記的每張受管表單分派給示範機構(已分派的略過),再跑開通腳本。
- 表單代號一律用底線(底座 `FORM_KEY_PATTERN` 不收 `-`);上表其餘表單的代號由各自的表單票改。
- **申請人也是審核者時**(底座每關三選一,預設剔除申請人):每家分店只有一位店長,店長自己送出、而那一關只有店長能審的單照預設會找不到審核者而卡住,所以申請人可能同時是審核者、又沒設自動通過的關卡一律設「照常審核」(`onboarding/form-workflows/types.ts` 的 `applicantReviews`;申請人留在名單、自己再按一次核准);撤銷售出、現金更正、盤點確認設「自動通過」;結帳確認第 1 關(接班人)維持預設,因為接班人不能是自己。每關的設定由 `onboarding/form-workflows.test.ts` 鎖住。
- 開通腳本只建立還沒有的流程,**已建立的流程不會改**;開通早於這項設定的租戶,要由租戶管理員在流程管理把上表的關卡改成「照常審核」並發布(或租戶還沒有資料時重新開通)。
