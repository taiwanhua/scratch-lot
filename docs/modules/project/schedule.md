# 班表管理(技術)

排班與出勤(專案規格第 14 章)的內部技術文件:群組 `schedule` 與四個子模組 `schedule.my`、`schedule.manage`、`schedule.settings`、`schedule.attendance`。租戶使用者看的說明在 `apps/admin/src/md/module-help/project/additions/schedule.<子模組>.help.md`。

## 用途

- **獨立的專案模組**:不引用刮刮樂的任何資料表或程式(依賴方向:刮刮樂 → 排班,`apps/api/src/project/project-lint.test.ts` 守)。刮刮樂要在排班畫面上顯示東西、或擋排班的刪除,經下方「給刮刮樂的登記接縫」登記。
- 本文件目前寫到:模組宣告與權限、排班設定(排班人員、人力需求範本、人力需求週範本、規則)、行事曆、畫休(我的畫休、畫休總覽、代改、畫休規則、開放 / 截止通知)、支援需求單、排班表(人力需求、排班、填進執行任務、兩種對話框、班表檢視)、檢核與發布(排班類規則、檢核面板、發布、發布後異動與通知)、套用範本與自動排班(含清除自動排入的人)、我的班表與打卡、出勤紀錄與補打卡申請(含排班作業的未對應排班的打卡)。

## 規則

### 組織鏈與「看得到上層」

範本、週範本、規則、行事曆都「沿組織樹往上找」:組織鏈 = 自己 → 上層 → … → 最上層組織(不含根組織)。這幾張表宣告「上層沿用到下層」:分店的人直接看得到所屬組織上層鏈建的,查詢以操作者的上下文、配**明列的組織鏈**條件;組織名稱以 `scheduleOrgReader`(可見範圍 ∪ 上層鏈)讀(`apps/api/src/project/schedule/shared/schedule-org.ts`)。根組織沒有排班(對根組織查 → `VALIDATION_FAILED`,欄位 `orgId`)。

### 排班人員(規格 14.3)

- **一人一份(規格 14.1:使用者子檔,一對一)**:同一租戶裡一個使用者只有一份排班檔案(唯一 `(tenantId, userId)`)。[加入排班] 建立時 `orgId` = 當前組織。讀取:可見範圍,加上可以排的分店有我的店(跨店支援也看得到,`staff.isShared = true`、標「其他店的排班人員(只能看)」);修改只限歸屬組織在可見範圍內的(別店建的 → `FORBIDDEN`,`reason: NOT_OWNER`);跨店支援由支援需求單把人加進那家店。
- **候選使用者** = 所屬組織落在操作者可見範圍內(且在當前組織的租戶裡)的使用者;[加入排班] 只能加這些人、而且整個租戶裡還沒有他的檔案(已加入 → `VALIDATION_FAILED`,欄位 `userIds`,同時加入也一樣;看不到 → `NOT_FOUND`)。檔案完全看不到的人(別店建的、可以排的分店也沒有我的店),候選清單標「已在其他組織加入」(`joinedElsewhere`)、勾選框停用;篩選時算「已加入」(`joined: true` 列出、`joined: false` 不列)。
- 可以排的分店只能加操作者看得到的(看不到 → `NOT_FOUND`)。存檔時 `orgs` 整份取代「操作者看得到的那幾家」;看不到的分店的關聯保留不動。
- **主要分店每人一家**:有任何可以排的分店時恰好一家(含看不到的分店的關聯一起算),否則 `VALIDATION_FAILED`(欄位 `orgs`)。主要分店在看不到的分店時列表回 `primaryElsewhere = true`。
- **候選人**(手動與自動排班同一份名單):`ScheduleStaffService.listScheduleCandidates(operator, orgId, at?)` —— 有排班檔案、啟用、帳號啟用、可以排的分店包含這家店的人;`at`(預設現在)只決定哪些關聯算數(那之前加入、那之後才拿掉的都算);回傳的 `canLead` / `isPrimary` / `sortOrder` 與排班檔案、帳號的啟用都是**現在的值**。這家店要在操作者的可見範圍內(排程以租戶系統身分呼叫 = 整個租戶),否則回空清單;候選人以租戶為邊界讀。

### 人力需求範本 / 週範本(規格 14.4)

- 可見 = 當前組織這一層 + 所有上層建立的;只有建立它的那一層能改 / 刪(看得到但不是這一層 → `FORBIDDEN`,`reason: NOT_OWNER`)。新增的屬於當前組織。
- 範本:名稱、簡稱 1–2 字、開始 / 結束 `HH:mm`(到分鐘,結束比開始早 = 跨午夜,不能相同)、崗位(「崗位」啟用中的選項,否則欄位 `positionKey`)、執行任務(負責人 0–1、協同 0–10;超過、或任務內容不是「執行任務」啟用中的選項 → `VALIDATION_FAILED`,欄位 `tasks`)、顏色(標籤色票代號或 null)。沒有休息、沒有適用星期。
- 週範本:7 格,每格只能選這一層看得到的範本(不認得的 id → `VALIDATION_FAILED`,欄位 `days`);已刪除的範本讀取時不列。
- 新增一筆負責人 / 協同時,畫面帶入規則「負責人 / 協同預設任務」的生效值。

自動排班條件(整組):`continuePreviousEntry` 延續同一人的排班(勾)、`leaderCountFirst` 負責人次數多者優先(勾)、`monthlyShiftBalance` 本月班數平均(不勾)、`allowOverlappingDemands` 允許同一人同時段填進多筆人力需求(不勾);勾選 = `enabled`、順序 = `order`。

- **生效值**(`apps/api/src/project/schedule/rules/rule-resolution.ts`):每條規則沿組織鏈找第一個有自訂的組織,找不到用程式預設;一列自訂的開關、值、等級、排序一起覆寫。**自動排班條件整組繼承**:鏈上第一個有任何一條自動排班條件自訂的組織,整組以它為準(它沒寫到的條件用程式預設)。
- **只有「人力不足」「同一時段兼多個崗位」可以關掉**(`isScheduleRuleToggleable`;自動排班條件的開關就是勾選);其他規則送 `enabled = false` → `VALIDATION_FAILED`(欄位 `enabled`)。
- **寫入**:[自訂] 寫本層一列(沒送的欄位照抄目前的生效值);自動排班條件自訂其中一條 = 整組寫成本層自訂。[還原] = 刪掉本層那一條(自動排班條件:整組)。最上層組織要 `edit-default-rules`、其他組織要 `edit-org-rules`(沒有 → `FORBIDDEN`,`reason: MISSING_PERMISSION`);沒有等級的規則送 `level` → `VALIDATION_FAILED`。
- **值只留定義裡的欄位**:存檔前丟掉多送的 key(預設休息每一級只留 `minMinutes` / `breakMinutes`;`pickScheduleRuleValue`)。
- **下拉值要是啟用中的選項**:「負責人 / 協同預設任務」的兩個 key 要是欄位管理「執行任務」啟用中的選項(否則 `VALIDATION_FAILED`,欄位 `value.<key>`)。
- **來源顯示**:本層自訂 →「本店自訂」(最上層組織「本層自訂」),摘要寫「本店自訂:6 天」;沿用 →「沿用:<上層組織名稱>」,上層組織操作者看不到時 api 回 `sourceOrgName: null`、畫面寫「沿用上層設定」;都沒設 →「系統預設」。自訂的列下方灰字「上層:<值>」= 上層的生效值。
- **檢查函式**(違反哪些規則)不在這裡:`apps/api/src/project/schedule/rules/rule-registry.ts` 的 `registerRuleEvaluator(key, evaluator)` 由各功能登記(畫休類規則、排班類規則);手動排班、自動排班、檢核面板、發布都呼叫同一個檢查函式、吃 `ScheduleRulesService.effectiveSettingsForOrg(operator, orgId)` 的生效設定。

### 排班表(規格 14.4「手動新增」、14.5「排班表」)

- **人力需求**(`schedule_demands`):日期、時間(開始 / 結束時點;結束不晚於開始 = 跨午夜,最長 24 小時)、崗位(「崗位」啟用中的選項,否則欄位 `positionKey`)、執行任務(負責人 0–1、協同 0–10,任務內容是「執行任務」啟用中的選項,否則欄位 `tasks`)。`date` 由 api 依租戶時區算(開始時點那一天)。沒有休息。
  - 新增時可帶 `templateId`(班表人力需求區點某一列範本的空白格;要是這家店組織鏈上看得到的範本,否則欄位 `templateId`),那一筆就歸在那一列;沒帶 = 「臨」。
  - **同時存成人力需求範本**(只在新增):要 `schedule.settings.edit-templates`(沒有 → `FORBIDDEN`,`MISSING_PERMISSION`);同一個交易裡經 `ScheduleTemplatesService.saveTemplate` 建立一筆屬於當前組織的範本(時間、崗位、執行任務照這筆),人力需求的 `templateId` 指向它。
  - 修改:執行任務沿用既有的 `taskId`(職責不能改,改了 → 欄位 `tasks`)、沒有 `taskId` 的是新的一筆。**拿掉有人填的任務 = 解除那些人**;解除後一筆都沒填的排班一起刪除(回 `deletedEntryIds`);其中被收銀班次綁定的(`blockedEntryIdsOf`)→ 整筆擋下,`VALIDATION_FAILED` + `extensions.blockedEntryIds`。有人填的人力需求不能搬到別天(欄位 `startAt`)。
  - [刪除人力需求] = 解除全部執行任務(同上規則)後軟刪除。
- **排班**(`schedule_entries` + `schedule_task_assignments`):人員(新增時;要是這家店的候選人 `listScheduleCandidates`,否則欄位 `userId`;修改時不能改)、上下班時點(最長 24 小時)、休息分鐘數(整數、0 ≤ 休息 < 時長,否則欄位 `breakMinutes`)、填進的執行任務 `assignments[{ demandId, taskId }]`。
  - **至少一筆**(零筆 → 欄位 `assignments`);同一筆人力需求只能一筆(重複 → 欄位 `assignments`);人力需求要是這家店、同一天(`date` 相同)的,任務要存在;負責人任務只能填這家店可擔任負責人的人(原本就填著的不再檢查);別筆排班已經填的 → 欄位 `assignments`。兩個請求同時填同一筆任務由唯一索引擋下,回同一個錯誤。
  - **一個人同一時間只有一筆排班,跨店也不能重疊**(相接不算):以租戶為邊界讀這個人所有分店的排班(`roster/roster-people.ts`,`tenantBoundaryContext` 登記用途「以人為準的資料」),重疊 → 欄位 `startAt`。店休那天不能排,跨午夜的班連隔天一起看(欄位 `startAt`)。**畫休那段時間不能排**:以租戶 + 人查這個人的畫休(`ScheduleDayOffsService.unavailableOfPerson`,不經這家店的候選人 —— 修改舊排班時那個人已經不能排這家店也一樣擋),排班碰到的日子(跨午夜含隔天)有整天畫休、或和時段不可排重疊(頭尾相接不算)→ 欄位 `startAt`。
  - **先排班、後登記畫休**(使用者定案):畫休照樣可以登記 / 代改;那段時間已經有這個人的排班(整個租戶,跨店也算)時,`addMyScheduleDayOffs` / `addScheduleDayOffsOnBehalf` 的回應附 `entryConflicts`(日期、上下班時點、分店名稱;看不到的分店 `orgName = null`),畫面提醒「這天已經有排班(…),請通知店長調整班表」。「畫休日有排班」另列進檢核面板(檢核的功能做)。
  - 修改時填進紀錄改成送來的那份:拿掉的軟刪除、新的建立(來源手動);沒變的保留原來的來源(自動排入的被手動改過才變成手動)。
  - **刪除**:被收銀班次綁定 → `VALIDATION_FAILED` + `extensions.blockedEntryIds`;否則軟刪除排班與它的填進紀錄。
  - **移除這天所有排班**:被綁定的略過,回 `deletedIds` / `skippedIds`。已發布後才需要的異動原因由發布的功能加上。
- **同時送出**:同一家店同一個月的寫入在交易一開始對 `schedule_periods.version` `$inc`(文件在交易外先建好),互相衝突、由 `TransactionService` 重跑。新增 / 修改排班另先對這個人的守門文件 `schedule_entry_locks` `$inc`(一個租戶一人一筆;`shared/schedule-person-locks.ts`,以 `tenantBoundaryContext` 寫,用途「例外寫入」):同一個人在**兩家店**同時被排、時間重疊時兩個交易在這筆文件上衝突,重跑的那一方讀到對方的排班而被擋下。畫休的登記 / 代改 / 刪除也在交易一開始碰同一份「人」守門文件(`schedule-day-offs.service.ts` 的 `ensureLocks` / `touchLocks` 呼叫 `SchedulePersonLocks`),排班與畫休同時寫同一人互相衝突、不會互相繞過。不放在 `schedule_staff` 上,是因為那筆是使用者會看、會改的檔案,`$inc` 會連帶改它的 `updatedAt / updatedBy`。
- **讀取**(`scheduleRoster`):這家店要在可見範圍內(`resolveScheduleOrg`;看不到 → `NOT_FOUND`),之後才呼叫「空清單分不出看不到」的 `listScheduleCandidates` / `listUnavailable`。人 = 候選人 + 這個月在這家店有排班、已不是候選人的人(`isCandidate = false`,依姓名 zh-Hant 排在後面)。一併回:人力需求(每筆執行任務帶填的人)、排班(`deletable` = 沒被綁定)、這些人在其他分店的班(看不到那家店 `orgName = null`,畫面寫「已排於其他分店」)、畫休、行事曆、這家店看得到的範本、規則的生效值(預設休息、負責人 / 協同預設任務、每月最多 / 最少畫休)、崗位註記(`positionAnnotationsOf`)。
  - **週檢視跨月**:另給 `from` / `to`(`YYYY-MM-DD`,要一起給、`from` 不晚於 `to`、只能落在這個月前後 6 天內,否則欄位 `from` / `to`)時,人力需求、排班、別家店的班、畫休、行事曆改讀「這個月 ∪ from–to」(`rosterReadRange`);人員統計與發布狀態仍只算這個月。人力需求帶 `createdAt`(時間軸平手排序)、填進紀錄帶 `reason`(自動填進的理由,長條滑過提示)。
- **統計欄**(`roster/roster-stats.ts`,這家店這個月):班數、負責班數(以排班為單位:任一筆填進的是負責就算 1 班)、總工時(每筆下班 − 上班 − 休息,分鐘)、畫休天數(同畫休規則 `dayOffDates`:那天有任何畫休就算 1 天;另回整天畫休天數與只有時段不可排的日子與時段)、最長連續上班(有排班的日子,含其他分店)。
- **[⚙ 顯示欄位]** 存個人偏好 `scheduleRosterColumns`(統計欄 key 逗號分隔,`apps/api/src/project/user-preferences.ts` 登記;定義在 `@repo/domain/project/schedule-settings` 的 `roster.ts`)。
- 前後端共用的純函式(`@repo/domain/project/schedule-settings` 的 `roster.ts`):預設休息(`defaultBreakMinutes`:長度已達門檻的級距中最高的那一級)、選人力需求自動填第一個空的執行任務(`pickOpenTask`)、負責人時間涵蓋(`leaderCoverageGaps`)、總工時寫法(`formatWorkMinutes`)。

### 檢核與發布(規格 14.2 等級、14.5「檢核面板」「發布」、14.1 `schedule_changes`、3.4 排班發布 / 異動)

- **排班類規則的檢查函式**(`apps/api/src/project/schedule/check/roster-rules.ts`,純函式,登記在 `registerRuleEvaluator`;畫休類由 `day-offs/day-off-rules.ts` 登記):
  - `maxConsecutiveWorkDays` 最多連續上班(人):有排班(任何分店)的日子連續超過 N 天;前後各讀 31 天,跨月的連續也算。
  - `minRestBetweenShifts` 兩班之間最少休息(人):**相鄰兩個上班日**,前一天最後下班到後一天第一次上班不到 N 小時(剛好 N 小時通過);同一天的多段排班之間不算。
  - `maxDailyWorkHours` 每天最多上班時數(人):同一天(`date`,跨午夜算開始那天)所有排班(同店多段、跨店)的「下班 − 上班 − 休息」加總超過 N 小時(8 小時:8:00 通過、8:01 違反)。
  - `multiPositionOverlap` 同一時段兼多個崗位(人,預設關閉):同一筆排班填進的人力需求(各自截到排班時間)兩兩有重疊;時間相接不算。
  - `understaffed` 人力不足(店):依時間切段檢查空的執行任務 —— 沒人填 = 整段缺;有人填、但那筆排班只涵蓋一部分 = 沒涵蓋的那段缺;同一筆人力需求同一職責的缺額依時間切段、相鄰同數合併,一段一項。附那段時間**可排**的人數(可以排這家店、沒有畫休、沒被任何分店的排班占用;負責另要可擔任負責人)與不能排的原因人數(不能擔任負責人 → 整天畫休 → 時段不可排 → 已排其他班,每人只算第一個)。店休那天的人力需求不檢查。
- **彙總**(`check/schedule-check.service.ts` 的 `evaluateSchedule(operator, orgId, month)`):用**最新的生效設定**跑一家店一個月的全部規則,再加上不屬於規則的檢核類別:
  - 人的排班類規則用那個人**主要分店**的設定(主要分店不一定看得到:以 `tenantBoundaryContext` 讀,登記用途「以人為準的資料」);只列**牽涉到這家店排班**的違反。
  - 畫休類規則(P07 的檢查函式)列以這家店為主要分店的人;同日最多畫休人數用這家店的設定。
  - `dayOffEntryConflict` 畫休日有排班(先排班、後登記畫休;使用者 10/21 定案,等級提醒):可以排這家店的人,這個月的排班(**含其他分店**)碰到他的整天畫休或和時段不可排重疊;別家店的排班帶 `isOtherStore`,看不到那家店 `orgName = null`。
  - 排序:限制在前、提醒在後;同等級依規則排序(這家店生效設定的 `order`,不屬於規則的類別在最後)→ 日期 → 姓名(zh-Hant)。
  - 每項的 `date` 是 [查看] 要捲到的那一天(這個月內),有 `userId` 的捲到 `userId|date`、店的項目捲到 `|date`(找不到時頁殼退回那一天)。「未對應排班的打卡」由打卡的功能追加一類 `key`。
- **等級**:限制 → 不能存、不能發布;提醒 → 照存照發布。
  - **存排班**(`saveScheduleEntry`)在寫入的交易內跑這個人的排班類規則(他主要分店的設定,`limitViolationsOfEntry`):存檔後**限制**的違反比存檔前嚴重(每條規則超出規則值的總量變大)→ `VALIDATION_FAILED`(欄位 `rules`)+ `extensions.violations`(`key`、`level`、`message`、`actual`、`limit`、`from`、`to`;只列這次造成的)。人力需求的新增 / 修改 / 刪除、刪排班、移除這天所有排班不跑規則(它們不會讓人的規則變嚴重;人力不足要靠排人補,刪人力需求不擋)。
  - **改規則不改已排的班**:已存的排班照留,檢核與發布用新的設定重新標示。
- **發布**(`publishSchedule`,`schedule.manage.publish`;`check/schedule-publish.service.ts`):這個月還沒有狀態文件時先建(未發布);用發布當下的設定重查整月,有限制 → `VALIDATION_FAILED` + `reason: HAS_LIMIT_VIOLATIONS`(`limitCount`);以「狀態仍是未發布、版本沒變」為條件更新成已發布(`publishedAt`、`publishedBy`)並 `$inc version`(和同月的寫入互相衝突)。查完到寫入之間有人改了排班(版本變了)→ 重查,最多 3 次,仍不行 → `reason: CHANGED_DURING_PUBLISH`;已發布 → `reason: ALREADY_PUBLISHED`;自動排班鎖定中(`lockedAt` 在 10 分鐘內)→ `reason: AUTO_RUN_IN_PROGRESS`(條件更新也帶「沒鎖或已逾時」,查完才被鎖的重查後回同一個原因)。**沒有取消發布的端點**。發布後通知這個月在這家店被排到的人(`schedule.published`,`dedupeKey` = `schedule.published:<分店>:<月份>`)。
- **發布後異動**(`changes/schedule-changes.service.ts`):寫入在交易一開始碰 `schedule_periods` 時讀到這幾個月有已發布的 → 輸入的 `changeReason { reasonKey, reasonNote }` 必填(欄位管理「排班異動原因」啟用中的選項;沒給 / 不是選項 → 欄位 `reasonKey`;選「其他」沒說明 → 欄位 `reasonNote`)。每筆異動寫一列 `schedule_changes` 並通知牽涉的人(`schedule.changed`,`dedupeKey` = `schedule.changed:<異動 id>`,內文帶原因的顯示名稱與說明):排班 = 那個人;人力需求 = 改之前填它的人(含因此解除 / 刪除排班的人);移除這天所有排班 = 每筆刪掉的排班各一列(原因只填一次)。未發布的月份不用原因、不記異動。

### 套用範本與自動排班(規格 14.4「套用範本」、14.5「自動排班」、14.1 `schedule_auto_runs` / `schedule_periods` 鎖定)

- **套用範本**(`schedule.manage.edit`;`auto-run/schedule-auto-run.service.ts` 的 `applyTemplates`,規劃是純函式 `auto-run/template-apply.ts` 的 `planTemplateApply`,預覽 `scheduleTemplateApplyPreview` 與套用 `applyScheduleTemplates` 用同一個):
  - 人力需求範本(可多選):加到選取的每一天;同一天**開始、結束時點與崗位都相同**的(不論來自哪個範本、也算這次前面已產生的)略過,只是時間重疊的照常產生。
  - 人力需求週範本(單選,要啟用中):依星期幾(`days[0]` = 星期日)用那一格的範本,**只補完全沒有人力需求的日子**;已有任何人力需求的日子算「略過的天數」。
  - 範本 / 週範本要是這家店組織鏈上看得到的(否則欄位 `templateIds` / `weekTemplateId`);日子要是這個月的(欄位 `dates`);店休的日子不產生。範本的 `HH:mm` 依租戶時區換成時點,結束不晚於開始 = 跨午夜。
  - 產生的人力需求:複製執行任務、每筆產生新的 `taskId`;`templateId` = 範本;`source` = `template` / `week-template`(自動排班補上的 = `auto`)。稽核一筆 `schedule-demand.apply-templates`。寫入照排班表其他寫入在交易一開始碰 `schedule_periods.version`;已發布的月份要異動原因,每筆記一筆 `demand.create` 異動(沒有牽涉的人,不通知)。
- **自動排班**(`schedule.manage.auto-run`;`runScheduleAutoRun`,只能在未發布):
  1. **鎖定這個月**:以條件更新標記 `schedule_periods.lockedAt` / `lockedBy`(條件:未發布、沒鎖或已逾時 10 分鐘,`SCHEDULE_AUTO_RUN_LOCK_MS`);拿不到 → `VALIDATION_FAILED`(欄位 `month`)+ `reason: AUTO_RUN_IN_PROGRESS`(已發布 → `ALREADY_PUBLISHED`)。鎖定中,別人的套用範本、清除、排班表的人力需求 / 排班寫入(`touchPeriods`)都回 `AUTO_RUN_IN_PROGRESS`;`scheduleAutoRunStatus.running` 讓別人的畫面顯示「自動排班執行中」。執行完(成功或失敗)解除自己標的鎖。
  2. **計算在交易外**(已持有月鎖,`prepareRun`,不寫資料):有勾「先以週範本補上」且這家店的規則「預設人力需求週範本」可用時,用同一個規劃算出要補的人力需求(先產生 id 與 `taskId`,`source = auto`;有 `auto-run` 就能補,不需要 `edit`)→ 依方式算出要清的填進紀錄(重排自動排入的人 = 只清來源自動的;全部重排 = 全清;清完零筆的排班一起刪,已被收銀班次綁定的那筆整筆留著)→ 把補上的當作已存在、要清的當作已不在,填人(`autoSchedule`)。
  3. **交易內只寫入**(`writeRun`):先重核月鎖仍是自己標的(計算期間逾時被別人重新標記 → `AUTO_RUN_IN_PROGRESS`,什麼都不寫、別人的鎖照留),碰 `schedule_periods.version` 與每位候選人的「人」守門文件(和同月 / 同一人的寫入互相衝突)→ 建補上的人力需求 → 清除 → 記執行紀錄 `schedule_auto_runs` → 新建 / 延長排班、建填進紀錄(`source = auto`、`autoRunId`、`reason`)。稽核 `schedule-auto-run.run`。
  4. **條件**:輸入的 `conditions`(勾選與順序,畫面預設帶這家店的生效設定 —— 整組繼承 —— 只用在這一次,不改設定);快照記在執行紀錄。執行紀錄記下這次實際用的整組條件與順序:輸入沒列的條件補在後面、視為不勾。延續延長的既有排班記在 `extendedEntries`(延長前 / 後的上下班時間與休息)。
- **填人的演算法**(`auto-run/auto-schedule.ts` 的 `autoSchedule`,純函式;**演算法版本 `SCHEDULE_AUTO_RUN_ALGORITHM_VERSION` = `"1"`**,改了處理順序、排序鍵、亂數取法或可排的判斷就加 1):
  - **處理順序固定**:範圍內(店休那天除外)的人力需求依日期 → 開始時間 → id;同一筆裡負責人任務先、協同依陣列順序;已有人填的任務跳過。候選人 = `listScheduleCandidates`,依 userId 排。
  - **亂數**:系統產生 32 位元種子(`newAutoRunSeed`,使用者看不到、記在執行紀錄);可指定種子的產生器 `seededRandom`(mulberry32)。每一筆任務對每位候選人(依 userId)各抽一次(已有人填的任務也抽),抽的次數不受誰可排影響。
  - **可排**(一定遵守):負責任務只給這家店可擔任負責人的人;同一筆人力需求同一人只填一筆;候選人在這家店有**同一天、時間相接或重疊**的排班 → 併進那筆(必要時延長上下班時間、休息取「原本」與「預設休息依新長度」較大者;相接 / 重疊的有兩筆以上 → 不排),否則新建一筆(時間 = 人力需求的時間、休息依規則「預設休息」);排班最長 24 小時;和自己其他排班(任何分店)不重疊;不碰整天畫休 / 時段不可排(頭尾相接不算);排班碰到的日子(跨午夜含隔天)不是店休;沒勾「允許同一人同時段填進多筆人力需求」時,併進的那筆排班已填的人力需求不能和這筆時間重疊;**限制等級的人的規則**(最多連續上班、兩班之間最少休息、每天最多上班時數、同一時段兼多個崗位;用他主要分店的設定 `ScheduleCheckService.personSettings`)排進去之後不能比排之前嚴重(同手動存排班的判斷 `limitSeverityByKey`)。
  - **排序鍵**(依勾選順序組成字典序,前一個平手才比下一個;都平手 → 亂數小的先):

    | 條件                                     | 比較                                                                                                                      |
    | ---------------------------------------- | ------------------------------------------------------------------------------------------------------------------------- |
    | `continuePreviousEntry` 延續同一人的排班 | 會併進既有排班(同一家店、同一天、時間相接或重疊)的先                                                                      |
    | `leaderCountFirst` 負責人次數多者優先    | 只比負責任務:過去 90 天(今天以前,租戶時區)在**這家店**擔任負責人的次數(以排班為單位:一筆排班任一筆是負責就算 1 次),多的先 |
    | `monthlyShiftBalance` 本月班數平均       | 這家店本月的排班筆數(含這次已排進的新排班),少的先                                                                         |

  - **自動排入理由**(`reason`,滑過長條提示):決定勝負的那個條件 —「自動排入:延續同一人的排班」「…:負責人次數較多」「…:本月班數較少」;只有一位可排 →「…:唯一可排的人」;沒勾排序條件 →「…:隨機」;都平手 →「…:條件平手,隨機」。手動改過(來源變手動)的不再回傳理由(資料庫照留)。
  - 排不滿的任務計入 `stats.unfilledCount`,檢核的「人力不足」照常列出原因。
- **清除自動排入的人**(`clearScheduleAutoAssignments`,`auto-run`,只能在未發布):範圍內人力需求上**來源 = 自動**的填進紀錄軟刪除;之後沒有任何填進的排班一起軟刪除(已被收銀班次綁定的那筆整筆留著);**被延續延長的排班縮回延長前的時段**(使用者 10/21 定案):依執行紀錄的 `extendedEntries` 由新到舊,排班目前的時間仍等於那次延長後的才縮回;延長後被手動改過(存檔後來源變手動,填進不會被清)→ 不縮回、維持現狀。只在「清除自動排入的人」縮回;「重排自動排入的人」清除時不縮回。稽核 `schedule-auto-run.clear`(含縮回的排班)。不做「復原這次自動排班」。
- **手動改過 → 手動**:`saveScheduleEntry` 修改時,留下來的自動填進紀錄來源改成手動(自動排入標記消失,不會被「清除自動排入的人」清掉)。
- **狀態與預覽**:`scheduleAutoRunStatus`(`view`)回 `canAutoRun`、`running`(別人的鎖定中)、最近一次的摘要(`latest`:時點、執行人、填入人次、補上的人力需求筆數 / 天數)、套用範本的週範本選項、條件的生效設定;`scheduleAutoRunPreview`(`auto-run`)回範圍內的人力需求筆數、可以補上的週範本與天數、手動 / 自動排入的人次(「全部重排」確認與「清除」的人次)。範圍內沒有人力需求、也沒有可以補的週範本 → 畫面停用 [執行](SC-20c)。

### 行事曆(規格 14.5)

- 某家店某天以**最接近的那一層**為準(`apps/api/src/project/schedule/calendar/calendar-resolution.ts`):上層設店休、本店沒設 → 本店那天店休;本店自設特殊日 → 以本店為準。同一層同一天只有一筆(重複 → `VALIDATION_FAILED`,欄位 `date`)。
- 特殊日:類別(欄位管理「特殊日類別」啟用中的選項,否則欄位 `category`)、名稱必填,顏色選填;店休:類別與顏色一律存 null。
- 寫入要 `schedule.manage.edit-calendar`,寫在選的那家店那一層;上層設的那一天本店改不了(`FORBIDDEN`,`NOT_OWNER`)。排班作業共用 `ScheduleCalendarService.effectiveDays(operator, orgId, from, to)`。

### 畫休(規格 14.1 `schedule_day_offs`、14.2、14.5「畫休總覽」、14.6「我的畫休」)

- **讀取以人為準**:那段時間這個人可以排的每一家店都不能排(查詢以 `tenantId` + `userId` 為準,不看歸屬組織)。**歸屬組織**(`orgId`,不共用):本人登記 = 當前組織;代改 = 畫休總覽選的那家店。整天畫休一天一筆(重複 → `VALIDATION_FAILED`,欄位 `kind`;同時送出由唯一索引擋下,回同一個錯誤);時段不可排一天可以多段,`HH:mm`、結束晚於開始、不跨午夜,和同一天既有的或同一次送的其他段重疊 → `VALIDATION_FAILED`(欄位 `slots`,相接不算重疊)。整天 + 時段可以同一天並存。
- **畫休的算法**(`apps/api/src/project/schedule/day-offs/day-off-rules.ts`):那一天只要有任何一種就算 1 天、1 人;「最多連續休假」只算整天畫休(跨月也連續)。
- **檢查函式**:畫休類四條規則(`maxMonthlyDayOffs`、`minMonthlyDayOffs`、`maxConsecutiveDaysOff`、`maxDailyDayOffStaff`)由 `ScheduleDayOffsService` 啟動時以 `registerRuleEvaluator` 登記;資料由呼叫端準備:人的規則給這個人前後各一個月的畫休,店的規則給**以這家店為主要分店的人**的畫休。違反附 `detail`(`actual`、`limit`、期間類的 `from` / `to`)給畫面組文案。
- **用哪家店的設定**:人的規則與開放期間都用這個人的**主要分店**的生效值;同日最多畫休人數檢查主要分店那一天。
- **同時送出**:登記 / 代改 / 刪除把「讀畫休 → 檢查重疊 → 跑規則 → 寫入」放在同一個交易,交易一開始對守門文件(主要分店 × 月份,`schedule_day_off_locks`)`$inc`(整天畫休另碰前後一個月:最多連續休假會跨月;碰不到文件 → 丟錯,不靜默失去保護);同一家店同一個月同時進來的寫入互相衝突、由 `TransactionService` 重跑,同日人數、每月上限、時段重疊不會被同時送出繞過(守門文件在交易外先建好)。
- **存檔規則**:存檔後限制等級的違反比存檔前多(新的、或超出更多)→ 不存,`VALIDATION_FAILED`(欄位 `date`,`extensions.violations` 列出擋下的違反);提醒照存,回在 `violations`。「每月最少畫休」不擋存檔(登記途中本來就不足,擋刪除會讓人改不掉登記錯的那天),照樣列在違規清單。
- **開放期間**(規則 `dayOffWindow`,`apps/api/src/project/schedule/day-offs/day-off-window.ts`):目標月的開放期間 = 前一個月的 N 日至 M 日(超過月底用月底);今天(租戶時區,`ScheduleClock`)在期間內 = 開放中。這條規則沒有等級,只看值、不看開關,登記檢查與通知用同一個判斷(`dayOffWindowValueOf`)。**本人**只能在開放中登記 / 刪除那個目標月的畫休,其他時候 → `FORBIDDEN`(`reason: OUTSIDE_DAY_OFF_WINDOW`)。
- **代改**(`edit-day-offs`):對象要是選的那家店(要看得到)的排班人員(否則 `NOT_FOUND`);不受開放期間限制;那個月的截止日(對象主要分店的開放期間)已過 → `reason` 必填(欄位管理「代改畫休原因」啟用中的選項),選「其他」`reasonNote` 必填(否則 `VALIDATION_FAILED`,欄位 `reason` / `reasonNote`);截止前原因選填。記代改人 `by`;代改刪除先寫入代改人與原因再軟刪除。代改一樣跑規則。
- **畫休總覽**:候選人(可以排這家店的排班人員)這個月的畫休;同日畫休人數只計 `isPrimary` 的人;「尚未畫休」= 主要分店是這家、這個月還沒畫任何一天的候選人。
- **給其他功能**:`ScheduleDayOffsService.listUnavailable(operator, orgId, from, to)` 回這家店的候選人每人每天的整天畫休 / 時段不可排(只列有畫休的日子;這家店要在操作者的可見範圍內,否則空清單)。**空清單分不出「沒有畫休」與「看不到這家店」**:呼叫端(排班表、自動排班)要先自己確認看得到這家店(例:`resolveScheduleOrg`,看不到 → `NOT_FOUND`),再呼叫它。

### 支援需求單(規格 8.9、14.10)

分店人力不足時請總部協助;總部在排班作業排好人後核准(支援指派單已取消:看得到兩家店的人直接在排班作業排人)。

- **表單**:受管表單 `support_request`(`apps/db-migrator/seeds/project/revisions/support_request.r3.seed.ts`,在 `seeds/project/registry.ts` 登記;部署時由受管定義 CLI 發布成共用表單,掛在 `schedule.manage`)。表單、提交、修訂、流程都用底座的表單引擎與流程引擎(`form_submissions`),沒有自己的資料表。
- **欄位**:日期(`date`,必填)、崗位(`position`,欄位管理「崗位」`schedule-position`,必填)、開始 / 結束(`start_time` / `end_time`,`HH:mm` 24 小時制,必填,結束要晚於開始;**不能跨午夜**,跨過午夜的需求拆成兩筆)、需要人數(`headcount`,1–99 的整數)、分店(`branch`,組織引用,預設目前組織,必填;Figma SC-14 有這一欄,讓總部看得出是哪家店)、說明(`note`,200 字內)。摘要:標題 = 說明、日期 = 日期;頁籤標題「支援需求單 <日期>」。
- **單號**:受管表單宣告 `serial: { prefix: "SP", period: "none", digits: 4 }`,第一次送出時給號,例 `SP-0001`(每個租戶各自計數、不分期間;存草稿不給號;機制見底座 `docs/modules/forms.md`「單號」、ADR-0015)。
- **沒有草稿**:表單「允許存草稿」關(seed 宣告 `allowDraft: false`),新增頁只有 [送出](`docs/modules/forms.md`「允許存草稿」)。
- **權限**:看列表與詳情 = `schedule.manage.view`(分頁也看它);新增 = `schedule.manage.create`;審核不看頁面權限(承辦人就能審,`docs/modules/workflows.md`)。
- **表單要先分派**:受管表單是共用表單,租戶要平台管理員在表單管理「分派租戶」後才看得到、才能新增(分派是各環境的資料,不在 seed)。示範指令 `demo create` 由平台管理員建完示範機構後自動分派 registry 登記的每張受管表單;真實租戶由平台管理員分派。
- **列表欄位**:讀 `schedule.manage` 的列表欄位配置(`modules.settings.list`,平台管理員在「模組與權限」調整)。初值在 `apps/db-migrator/seeds/project/settings.ts`(初始 seed 值:模組的 settings 已存在就不覆寫):單號(摘要槽 `serialNo`)、日期、開始、結束、崗位、需要人數、分店 + 內建欄「狀態」(這份初值整份取代 `schedule.ts` 宣告裡的 `settings`)。

### 我的班表與打卡(規格 14.1 `schedule_attendance_punches`、14.6)

- **以人為準**:我的班跨分店合併顯示(支援的分店不一定在我的可見範圍)、打卡寫在班所在的分店 —— `my/my-schedule.service.ts` 以 `tenantBoundaryContext` 讀寫(用途「以人為準的資料」「例外寫入」);當前組織只用來決定租戶與「沒有排班」打卡的分店。
- **只有已發布的班**(`my/published-entries.ts` 的 `PublishedEntries.publishedOnly`):班所在的分店、所在月份的 `schedule_periods` 是已發布才算;未發布的班看不到、也不能打卡(`NOT_FOUND`)。給刮刮樂的查詢用同一支。
- **打卡**(`schedule.my.punch`;純函式 `my/punch-rules.ts`):在排班卡片上打 = 帶那一筆排班(要是自己的、已發布);**今天的班**上下班都能打,**昨天還沒打下班卡的班**只能打下班卡,其他 → `VALIDATION_FAILED`(欄位 `entryId`)。「沒有排班」打的卡記在當前組織、`entryId = null`(未對應排班,之後在出勤紀錄 / 排班作業對應)。時間由伺服器決定(`ScheduleClock`),記 `ip`(`req.ip`;api 依 `apps/api/src/http-proxy.ts` 信任 Cloud Run 前端的一層代理,取 `X-Forwarded-For` 最右邊的客戶端 IP)、`userAgent`。跨店不限。
- **重複打卡**:同一班同類型多張時上班取最早、下班取最晚,其餘標 `duplicate`。寫入一張就在同一個交易裡重算那一班的標記(`attendance/punch-ledger.ts` 的 `SchedulePunchLedger.markDuplicates`;補打卡核准、改對應排班、排班對話框對應打卡都呼叫同一支),交易一開始碰「人」守門文件(`schedule_entry_locks`),同一個人同時打兩張會衝突重跑。未對應排班的卡不標。
- **缺卡不存**,讀取時計算:只檢查**已結束**(下班時點 ≤ 現在)的班,上下班都檢查;打卡不完整提醒列最近 7 天(含今天)的。
- **打卡區**:今天的班(依上班時點)在前,再來是昨天未打下班卡的班;`hasEntryToday` 決定「沒有排班」區塊收合;`openUnmatchedClockIn` = 今天最後一張未對應排班的卡是上班卡。
- **最近異動**:讀 `schedule_changes` 裡牽涉我的(`userIds`)、異動那天 ≥ 今天的(只列還沒到的班),新到舊;原本 / 現在的時間取 `before` / `after` 的 `startAt` / `endAt`,原因是欄位管理「排班異動原因」的名稱。「新」由前端比對上次打開這一頁的時間(瀏覽器 localStorage `schedule.my.lastVisit:<userId>`)。
- **月曆的其他資料**:當前組織這個月的店休 / 特殊日(`effectiveDays`)、我這個月整天畫休的日子(`unavailableOfPerson`)。

### 出勤紀錄與補打卡(規格 14.5「未對應排班的打卡」、14.7、14.8)

程式在 `apps/api/src/project/schedule/attendance/`;純函式(遲到 / 早退 / 工時、補打卡的表單代號與欄位 key、存值解析)在 `@repo/domain/project/schedule-settings` 的 `attendance.ts`,api、admin、seed 共用。沒有新的資料表:讀寫 `schedule_attendance_punches` 與排班,補打卡申請用底座表單引擎的 `form_submissions`。

- **出勤紀錄**(`ScheduleAttendanceService`):
  - **員工只看自己的**:沒有 `schedule.attendance.view-all` 時,依人員(月)只能看自己(給別人的 `userId` → `FORBIDDEN` + `reason: MISSING_PERMISSION`)、依分店(日)只列自己的班與卡、Excel 只匯出自己的。看自己的以租戶為邊界讀(`tenantBoundaryContext`,用途「以人為準的資料」;支援別家店的班也列),看別人的照操作者的可見範圍。
  - 只列**已發布**月份的班(`PublishedEntries.publishedOnly`)。上下班卡 = 生效的那兩張(上班取最早、下班取最晚,同打卡規則)。
  - **遲到 / 早退**:用**班所在分店**的規則 `graceMinutes`(`lateGraceMinutes` / `earlyLeaveGraceMinutes`,預設各 5 分鐘);差距**大於**寬限才算(剛好 5:00 不算、5:01 算);**超過寬限時,遲到 / 早退的分鐘數以整分鐘無條件進位**(晚 5 分 1 秒 = 6 分,晚 11 分整 = 11 分)。狀態:已到(有上班卡)/ 未到(班已開始、沒有上班卡)/ 未開始。
  - **工時**:實際工時 = 下班 − 上班 − 休息(缺一張卡 = 沒有)、排班工時 = 排班下班 − 上班 − 休息;不做薪資計算。特殊日 = 班所在分店那天的行事曆(名稱、類別名稱);補卡註記 = 這一班有 `source = makeup` 的卡。
  - 依分店(日)的「未對應排班」= 當天在這家店打、`entryId = null` 的卡;排班人數 / 已到 / 未到不受「只看未對應排班的打卡」影響。不自動更新(沒有即時信號、不放刷新按鈕)。
  - **Excel**(`export`):api 回資料(選的組織與它看得到的下層分店、這個月的班,一家分店一組),admin 以輸出報表共用的 `buildWorkbook` 產生 —— **一家分店一個工作表**(工作表名稱 = 分店名稱),欄位依序:日期、人員、排班、上班、下班、在班時數(下班 − 上班)、休息、實際工時、排班工時、遲到、早退、特殊日類別、補卡註記(`apps/admin/src/lib/project/schedule-attendance.ts` 的 `attendanceSheetsOf`)。
- **改對應排班**(`reassign-punches`;出勤紀錄的 [改對應排班]):原因必填(欄位管理「改對應排班原因」`schedule-entry-reassign-reason` 啟用中的選項;沒給 / 停用 → `VALIDATION_FAILED` 欄位 `reasonKey`;選「其他」沒說明 → `reasonNote`)。可以選的排班 = 這個人打卡那天前後各一天、看得到的已發布排班(別人的排班 → `VALIDATION_FAILED` 欄位 `entryId`),或「沒有排班」(改成未對應)。**時間與類型不能改**。卡的分店跟著排班(別家店的班用搬家 `reassignOrg`,呼叫端登記在 `project/database/org-reassign-callers.ts`);原本那一班與新的那一班重算重複打卡。寫稽核 `schedule-punch.reassign`(`before.entryId`、`after.entryId` / `reasonKey` / `reasonNote`)。
- **排班作業的未對應排班的打卡**(規格 14.5):`scheduleRoster` 回這家店讀取範圍內打的、未對應排班的卡(`unmatchedPunches`,`attendance/unmatched-punches.ts` 的 `UnmatchedPunchesReader`)與規則「對應排班容許時間」(`settings.entryMatchToleranceMinutes`,預設 60)、`canUsePunchTime`(`schedule.manage.use-punch-time`)。存排班(`saveScheduleEntry`)可以帶 `punchIds`(勾選的卡:這個人在這家店、還沒對應的卡,不是 → `VALIDATION_FAILED` 欄位 `punchIds`),在同一個交易裡對應到這筆排班並重算重複打卡;`usePunchTime: true`(沒有 `use-punch-time` → `FORBIDDEN` + `MISSING_PERMISSION`)= 上班換成勾選的上班卡中最早的、下班換成下班卡中最晚的。檢核面板多一類 `unmatchedPunches`(提醒,一人一天一項,`actual` = 張數,不影響發布)。
- **補打卡申請**(受管表單 `makeup_punch`,`apps/db-migrator/seeds/project/revisions/makeup_punch.r2.seed.ts`,掛在 `schedule.attendance`):
  - **欄位**:日期(`date`)、分店(`branch`,組織引用,預設目前組織)、對應排班(`entry`:排班 id,或 `none` = 「沒有排班(臨時代班)」;`entry_label` 是送出當下的顯示文字,例「早 08:30–14:30」,選「沒有排班」時是「沒有排班(臨時代班)」;`entry` 設 `widget.hideWhenReadonly`,詳情與申請中心只顯示 `entry_label`,不露出系統 id)、類型(`punch_type`,`in` / `out`)、時間(`time`,`HH:mm`)、原因(`reason`,欄位管理「補打卡原因」)、說明(`note`;原因選「其他」必填)。單號 `serial: { prefix: "M", period: "none", digits: 4 }`(例 `M-0031`);**沒有草稿**(`allowDraft: false`);作廢原因 = 欄位管理「作廢原因」`void-reason`(刮刮樂與排班共用,`@repo/domain/project/reason-note` 的 `SHARED_FIELD_CATEGORY_KEYS`)。受管表單 r2(r1 保留不改)。
  - **對應排班必選**:新增頁選了日期與分店後列出本人當天在那家店的已發布排班(`makeupPunchEntryOptions`,經 `ScheduleEntryLookup.listEntriesOfDay`),最後一個是「沒有排班(臨時代班)」;改了日期或分店就清空重選;沒選 → 畫面擋「請選擇對應排班」。核准直接寫那一筆,**不自動找**。
  - **掛接點**(`attendance/makeup-punch-lifecycle.ts`,以 token `MAKEUP_PUNCH_SERVICE` 取 `MakeupPunchService`,避免登記檔 import 服務造成循環):`beforeSubmit` 檢查對應排班是本人那天在那家店的已發布排班(否則 `MAKEUP_PUNCH_ENTRY_MISMATCH`;沒選 `MAKEUP_PUNCH_ENTRY_REQUIRED`;欄位缺 `MAKEUP_PUNCH_INVALID_VALUES`;其他沒說明 `MAKEUP_PUNCH_NOTE_REQUIRED`);`beforeApprove` 選的那筆排班被刪除 → `MAKEUP_PUNCH_ENTRY_DELETED`(只能退回讓本人重選;只改了時間照常核准);`completed` 以系統身分(租戶邊界,用途「例外寫入」)寫一張打卡:`source = makeup`、`makeupRequestId` = 這張單(有值時部分唯一索引,同一張申請的完成同時跑兩次只寫得進一張)、`entryId` = 申請時選的那一筆(選「沒有排班」= 未對應排班,分店 = 申請的分店)、時間 = 那天的那個時間(下班卡早於排班上班時點 = 跨午夜的班,算隔天),再重算那一班的重複打卡;重送不重複寫。文案在專案字典 `admin.lifecycle.<碼>`(申請中心核准被擋也顯示)。
  - **我的班表的 [申請補卡]**:`my/ScheduleTab/makeup-punch.ts` 的 `useMakeupPunchLink()` 連到新增頁並帶入日期、分店、類型、對應排班(網址參數);`myPendingMakeupPunchEntryIds` = 我送出、還在審核中的申請選的排班,那一班顯示「補卡審核中」。沒有 `schedule.attendance.create` 就不顯示 [申請補卡]。
  - **審核畫面的警告**:依模組登記的審核擴充 `Review`(`app/project/workflow-extensions.ts` 登記 `MakeupPunchReview`;底座 `docs/modules/workflows.md`「依模組登記的審核擴充」):`makeupPunchEntryExists(submissionId)` = false → 我的任務上方顯示「對應的排班已被刪除」、回報 `approveDisabled` 停用 [核准]。模組詳情頁與申請中心詳情頁都生效;申請中心的批次核准不畫審核畫面,由掛接點 `beforeApprove` 擋下。`makeupPunchEntryExists` 查得到的人 = 讀得到這筆申請的人(底座唯一判準 `SubmissionReadAccess`):有 `schedule.attendance.view` 且照原規則讀得到(可見範圍 + 資料範圍)、申請人、這張申請流程上的審核者(現在或曾持有任務)、知會對象;其他人(含同租戶)回 `NOT_FOUND`。申請以讀者的租戶為邊界讀(底座審核流程的存取,不套 `form_submissions` 的資料範圍規則,審核者不會因資料範圍讀不到),排班以 `tenantBoundaryContext` 反查(用途「反查」);只回是 / 否。

## 錯誤碼

只用通用碼(GQL-04):`NOT_FOUND`(看不到)、`VALIDATION_FAILED`(`fields` 指到欄位)、`FORBIDDEN`(`reason`:`NOT_OWNER` 上層建立的、`MISSING_PERMISSION` 沒有這個組織要的規則權限、`OUTSIDE_DAY_OFF_WINDOW` 本人在畫休開放期間外修改)。自動排班鎖定 / 已發布:`VALIDATION_FAILED`(欄位 `month`)+ `extensions.reason`(`AUTO_RUN_IN_PROGRESS` / `ALREADY_PUBLISHED`;`auto-run/period-lock.ts`),前端 `scheduleErrorOf` 把 `AUTO_RUN_IN_PROGRESS` 細分成同名碼(`admin.schedule.errors.AUTO_RUN_IN_PROGRESS`),自動排班的對話框讀 `admin.schedule.roster.autoRun.errors.*`。畫休違反限制:`VALIDATION_FAILED` + `extensions.violations`。排班已被收銀班次綁定(刪排班、刪人力需求或解除任務連帶刪排班):`VALIDATION_FAILED` + `extensions.blockedEntryIds`(`roster/roster-error.ts`;前端 `pages/project/schedule/manage/roster/roster-error.ts`)。存排班違反限制:`VALIDATION_FAILED`(欄位 `rules`)+ `extensions.violations`;發布被擋:`VALIDATION_FAILED`(欄位 `month`)+ `extensions.reason`(`HAS_LIMIT_VIOLATIONS` / `ALREADY_PUBLISHED` / `CHANGED_DURING_PUBLISH` / `AUTO_RUN_IN_PROGRESS`);已發布後沒給異動原因:`VALIDATION_FAILED`(欄位 `reasonKey` / `reasonNote`)。格式對但不能存的情形另帶 `extensions.reason`(`shared/schedule-error.ts` 的 `SCHEDULE_REASONS`,唯一索引撞到時回同一個):`CALENDAR_DAY_DUPLICATE`(同一天已有行事曆)、`DAY_OFF_DUPLICATE`(已有整天畫休)、`TIME_RANGES_OVERLAP`(畫休時段重疊)、`NO_PRIMARY_STORE`(沒有主要分店)、`DEMAND_HAS_ASSIGNMENTS`(已有人排的人力需求改到別天)、`NOT_CANDIDATE`(不在排班名單)、`STORE_CLOSED`(店休)、`ENTRY_OVERLAP`(和另一筆排班重疊)、`DAY_OFF_CONFLICT`(和畫休重疊)、`PUNCH_UNAVAILABLE`(打卡已被對應)、`TASK_NOT_ON_DAY`、`CANNOT_LEAD`、`TASK_TAKEN`、`DEMAND_REPEATED`、`TASK_ROLE_LOCKED`、`ALREADY_JOINED`、`ORG_REPEATED`、`PRIMARY_ORG_REQUIRED`、`OPTION_DISABLED`(選項已停用)、`RULE_NOT_TOGGLEABLE`、`PUNCH_NOT_ALLOWED`、`CONCURRENT_EDIT`(同時修改)、`REFERENCE_NOT_FOUND`(選的排班、人力需求範本、週範本已不在或看不到;前端寫「請重新選擇」,不寫「必填」);沒有 reason = 格式錯或必填。前端:對話框把原因寫在 `fields` 指到的欄位下、提示只放通用句(REACT-18;`pages/project/schedule/schedule-field-errors.ts`,文案 `admin.schedule.errors.reasons.*`),對不到欄位的提示用 `scheduleErrorKey`。前端文案 `admin.schedule.errors.*`(`pages/project/schedule/schedule-error.ts`;檢核與發布的在 `manage/roster/check-panel/check-errors.ts`、`admin.schedule.roster.publish.errors.*`)。
