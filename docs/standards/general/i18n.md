# i18n(多語文案)

適用:所有出現在 UI 上的文字。套件:front 用 `next-intl`、admin 用 `use-intl`(同一生態、同一 API);訊息檔集中在 `packages/i18n`。

## I18N-01 UI 文案一律進 `@repo/i18n` 的訊息檔,元件不寫死

新增或修改介面文字時,改 `packages/i18n/messages/<locale>/<namespace>.json`,元件透過 `useTranslations` / `getTranslations` 取用。`ui` 套件的元件維持語言無關 — 文字一律由 props 傳入,`ui` 不 import 任何 i18n 套件。

例外:log、錯誤 code、開發者才看得到的字串不需要進訊息檔。

**ui 的登錄表可以帶預設顯示名,但必須可由呼叫端覆寫**:`@repo/ui` 的白名單登錄表(如 `module-icon-registry.ts` 的 29 個圖示短詞)為了讓 story / 測試 / 尚未接 i18n 的呼叫端有東西可顯示,允許在登錄表裡放一組繁中預設名;條件是元件必須開一個覆寫用的 prop(慣例 `labelOf?: (key) => ReactNode`),讓 app 從訊息檔接管。**覆寫函式回 `undefined` 時退回登錄表的預設名** — 這樣 ui 之後加新 key,訊息檔還沒補上也不會在執行期炸掉。ui 本身仍不 import 任何 i18n 套件。正本:`packages/ui/src/icons/module-icon-registry.ts`

## I18N-02 訊息檔結構:`<namespace>.json` 依 app 分,共用放 `common`

- `common.json`:跨 app 共用(品牌名等)
- `front.json` / `admin.json`:各 app 專屬,依「頁面或區塊」分第二層 key(如 `home.empty`)
- key 用 camelCase;新增 key 必須**同時補齊所有語言**(`zh-TW`、`en`),寧可先放英文原文也不能缺 key

## I18N-03 帶變數與複數用 ICU 格式,不做字串拼接

寫 `"total": "共 {count} 道食譜"` 然後 `t("total", { count })`;禁止 `t("total") + count` 這類拼接 — 語序在不同語言不一樣。複數用 ICU plural 語法。

## I18N-04 front 的站內連結用 `src/i18n/navigation.ts` 的 `Link`,不用 `next/link`

`next/link` 不會帶語言前綴,會把 `/en` 使用者踢回中文版。`redirect`、`useRouter`、`usePathname` 同理,都從 `navigation.ts` 匯入。

## I18N-05 URL 策略:預設語言無前綴

zh-TW(預設)走 `/`,其他語言帶前綴(`/en/...`),由 `apps/front/src/proxy.ts` 處理偵測與轉址。此決定影響 SEO,改動前先討論。

admin 的語言不進 URL,**跟著帳號**:正本是個人偏好 `user_preferences.settings.locale`,本機 `<slug>-admin-locale` 只是快取 —— 登入前(登入頁、設定密碼頁)與登入後等偏好回來的載入畫面用它,登出後保留。登入後帳號有語言就用帳號的並覆寫快取;沒有(新帳號)就沿用快取並寫回帳號。切換只在頭像選單,立即生效並同時寫入帳號與快取;寫入帳號失敗時畫面維持新語言並跳失敗提示,下次登入以帳號為準。外觀(`<slug>-admin-color-mode`)跟著裝置,只存本機。

正本:`apps/front/src/proxy.ts`、`apps/admin/src/lib/base/locale.ts`(`resolveAccountLocale`)、`apps/admin/src/hooks/base/useAccountLocale.ts`

## I18N-06 專案品牌由 app 注入字典,基礎字典只放中性預設

品牌名(`common.brand`)與前台 metadata(`front.meta` 的 `title` / `titleTemplate` / `description`)是專案值,正本在 `@repo/project-config/public`,不寫在訊息檔。訊息檔裡這四個鍵只放中性預設(讓鍵存在、字典檢查照常運作);換品牌不改字典。

- **注入點只有 app 的組裝處**:admin 的 `apps/admin/src/app/providers/AppProviders.tsx`、front 的 `apps/front/src/i18n/request.ts`,以 `composeProjectMessages({ brandName, frontMetadata })` 取得每個語系的完整字典再交給 `IntlProvider` / next-intl。元件照舊用 `t("brand")`、`getTranslations({ namespace: "front.meta" })` 取字,不直接讀專案設定。
- **`@repo/i18n` 不 import `@repo/project-config`**:值由 app 傳入。`composeProjectMessages` 只覆寫上述四個鍵,不做通用 deep merge、不增減鍵、不動 ICU 參數,也不修改基礎字典;`frontMetadata` 缺任何一個支援語系就丟錯,不退回中性預設。
- **專案值是純文字,由注入邊界編成 ICU literal**:字典是 ICU 訊息,品牌名與 metadata 卻是專案提供的純文字。`composeProjectMessages` 寫進字典前以 `encodeIcuLiteral` 編碼 —— 單引號寫成 `''`,從第一個 `{` 或 `<` 起把整段尾巴包進一組引號 —— 所以翻譯函式顯示的就是原文,`Acme {name}`、`Acme <x>`、`O'Brien` 都不會被當成參數、標籤或引號,也不必傳參數。專案設定裡照寫原文,**不要自己寫 ICU 跳脫**(會被再編一次、顯示出多餘的引號)。這個編碼只用在字典注入;信件與 HTML title 各有自己的 HTML 跳脫,不混用。
- **`titleTemplate` 的 `%s` 是 Next title template 的佔位**,對 ICU 而言是一般文字,原樣保留;這四個鍵不帶 ICU 參數。
- **新增語系**:訊息檔補齊(I18N-02)之外,專案設定的 `front.metadata` 也要補一份,否則 app 的型別檢查與 `composeProjectMessages` 都會擋下。
- **套件內拆檔**:`locales.ts`(語系定義)、`base-messages.ts`(基礎字典的唯一組裝處與 `Messages` 型別)、`icu-literal.ts`(純文字 → ICU literal)、`project-messages.ts`(注入);`index.ts` 只作出口,實作檔互相直接引用檔名、不回頭 import index(同 STRUCT-07 的規則,避免循環依賴)。
- **測試直接用基礎字典**(`messages`)只適合不顯示品牌的單一元件;要驗品牌文字就走 `renderApp`(經 `AppProviders` 注入)。
- **一般測試不寫任何專案的字面值**:讀正式設定的測試,期望值取自 `projectPublic` 本身(格式由測試自己寫,不呼叫受測函式推導),換專案只改專案值檔、測試不必跟著改。要固定某組值時用夾具,不讀正式設定:admin 以 jest project 頂替整張模組圖的專案設定 —— `*.alt-project.test.*`(替代品牌,`apps/admin/src/test/alternative-project.ts`)與 `*.legacy-project.test.*`(CookHome 歷史值,`cookhome-legacy-project.ts`,守既有瀏覽器的鍵、資料格式與原輸出);其他套件把夾具寫在測試檔內。
- **特殊字元以真的翻譯函式驗**:`apps/admin/src/app/providers/ProjectMessagesIcu.test.tsx` 用 use-intl 的 `useTranslations` / `createTranslator` 確認顯示原文、沒有 IntlError;`packages/i18n` 的測試只驗編碼後的字串與參數名。

正本:`packages/i18n/src/project-messages.ts`、`packages/i18n/src/icu-literal.ts`、`packages/project-config/src/project/public.ts`、`apps/admin/jest.config.mjs`
