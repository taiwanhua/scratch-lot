# 權限測試劇本(以示範模組驗證)

驗證對象:權限模型(ADR-0004)、查詢與判斷流程(ADR-0011)、資料範圍規則(ADR-0008)、移除所屬組織(ADR-0003)、管理範圍與可見範圍的分工(ADR-0005)、檔案儲存(ADR-0010)、表單引擎(`docs/concepts/form-engine.md`)、審核流程(`docs/modules/workflows.md`)。模組與資料定義見 [示範模組1](../modules/demo.sub.sample-one.md)、[示範模組2](../modules/demo.sample-two.md)、[示範表單](../modules/demo-form.md)。

1. **wildcard 涵蓋未來(同層)**:角色勾示範模組1 的 `demo.sub.sample-one.*`(存單筆);下一版 seed 對示範模組1 新增權限 → 不改角色即擁有;對其編輯頁(`…edit-page`)新增的權限**不**自動擁有(子模組由自己的 `*` 代表)。
2. **資料範圍規則**:建規則「套用對象=客服角色 → 建立者 = 【操作者本人】」→ 客服查示範項目僅見自建;刪規則 → 恢復可見範圍。
3. **未宣告對照**:示範模組2 查詢僅受可見範圍保底(規則機制不介入)。
4. **頂層合成**:建兩條都命中同一人的規則,切換 OR/AND 驗結果集為聯集/交集。
5. **欄位級(綁父)**:無 `show-internal-note` → 詳情/編輯頁無此欄、API 投影排除;有 show 無 edit → 唯讀;硬送該欄寫入 → 拒。
6. **頁面自有權限**:無 `edit-page.show-history` → 編輯頁無歷程區塊,編輯功能不受影響(兩者獨立);`create-page.show-tips` 同理。
7. **路由防守**:角色未綁新增頁模組 → 手打網址被擋;綁了新增頁但無 `create` 權限 → 頁進得去、送出被 API 擋(頁與功能分離)。
8. **組織外**:授予示範模組1 的角色後移除所屬組織(radio 選保留)→ 三處列表標示、功能仍可用、資料範圍縮小。
9. **移除三檔**:dry-run 清單:(b) 只列該組織擁有 vs (c) 加列失去子樹支撐 — 用多所屬組織帳號驗差異;對象還要持有一個「擁有組織在被移除組織的**上層**、但不包住他其他所屬組織」的角色,否則 (b) / (c) 列出來一樣(見下方劇本 9)。
10. **防越權**:矩陣只可勾操作者自身擁有的權限與模組。
11. **儲存雙路**:coverPath 公開 URL 直接顯示;attachmentPath 簽名下載,無 `view` 者 API 拒發。
12. **可見性開關**:ON→OFF 驗**業務資料**的名單與資料收縮、既有角色授予不動;治理頁(組織 / 使用者 / 角色)完全不動 — 見劇本 14。
13. **總覽也是模組**:角色未綁 `overview.*` → 登入後 `/` 轉到側欄第一個能進的頁(如 `/system/org-manager`),側欄沒有「總覽」列;手打 `/overview` 顯示無權限頁;綁上 `overview.*` → 登入落在 `/overview`(ADR-0011「路由與導向規則」)。
14. **管理範圍 vs 可見範圍**(CONTEXT.md 兩個詞條;ADR-0005 的分工表):
    - **前置**:管理範圍算的是**全部**啟用中角色的擁有組織子樹(不只治理角色)。甲身上若留著擁有組織 = 租戶頂層的角色(例如「客服」),樹根永遠是租戶頂層 —— 看樹根的小節先把那種角色拿掉。
    - **由角色決定、與所屬哪裡無關**:甲的所屬組織只有「南港店」,但持有一個擁有組織 = 租戶頂層的角色 → 組織管理頁的樹根是租戶頂層、整個租戶的組織與使用者都管得到;把角色換成擁有組織 = 南港店的那一個 → 樹根變成南港店,租戶頂層與其他分店**不出現**在樹上(不是灰的,是不回傳),`org(其他分店 id)` 回 `NOT_FOUND`。
    - **不受可見性開關影響**:把該租戶的開關設成 `own` → 上一條的結果完全不變(治理頁、角色候選、搬移候選都不動);同一個人去看業務模組(示範模組1)的清單則收縮成只剩所屬組織的資料 — 兩個範圍各管各的。
    - **多根**:先讓甲也加入內湖店(授予要過資格檢查,只屬南港店會拿到 `USER_NOT_ELIGIBLE`),再同時授予擁有組織 = 南港店與 = 內湖店(兩者沒有共同上層)的兩個角色 → 組織樹有**兩個根**;停用其中一個角色 → 那一棵子樹整個退出管理範圍。
    - **無治理角色 = 空**:把全部角色解除(或全部停用)→ 沒有任何治理權限,治理頁進不去(`FORBIDDEN`)。「硬給 `view` 但管理範圍是空的」在產品上**造不出來**(權限與管理範圍來自同一批啟用中角色,給了 `view` 就一定帶著那個角色的擁有組織),只由 api 測試覆蓋。
    - **可見性開關的權限搬家**:租戶管理員(模板副本,含 `system.org-manager.*`)在編輯**自己租戶頂層**時看得到「使用者可見自身組織的下層組織資料」開關並設得了;對**別的租戶**的頂層送出 → `NOT_FOUND`(管理範圍外);對非租戶頂層送出 → `VALIDATION_FAILED`;只持 `system.org-manager.view` 的人連「編輯」都沒有;持 `view` + `edit`、沒有 `set-visibility` 的人編輯彈窗裡沒有開關,兩者硬送都是 `FORBIDDEN`。
    - **搬移候選與租戶頂層保護**:候選 = 管理範圍 ∩ 同租戶 − 自己子樹;把租戶內的組織搬去別的租戶 → 範圍外即 `NOT_FOUND`(根組織看得到兩邊才會拿到 `CROSS_TENANT`),搬進自己的子樹 → `CYCLIC_MOVE`;租戶內的人搬租戶頂層本身 → `FORBIDDEN`。
15. **側欄商標繼承**(ADR-0010):租戶頂層設商標、下層不設 → 下層使用者的側欄顯示租戶的商標;下層自己設一張 → 改顯示自己的;把下層的清掉 → 又回到繼承來的那張(沿 `ancestors` 由近到遠找第一個有商標的上層)。
16. **租戶視角**:root 開通租戶(取消勾選示範群組)→ 租戶管理員登入:側欄無「模組與權限」「資料範圍」「示範群組」、組織樹以租戶頂層為根、沒有「開通租戶」按鈕;root 視角看得到新租戶並標「租戶」。
17. **擁有者保護**:租戶管理員試圖停用 / 移出租戶 / 解除自己(擁有者)的租戶管理員授予 → `OWNER_PROTECTED`;root 可執行;租戶內任何人對租戶頂層停用 / 刪除 / 搬移 → `FORBIDDEN`。
18. **表單生命週期**:root 在表單管理建共用表單 → 設計 → 存草稿 → 發布 → 分派給租戶A → +user 在示範表單(頂層)新增、填寫、送出 → 列表看得到那一筆、詳情看得到填的值。
19. **客製副本與退役**:+tenant 以分派來的表單為基底建客製表單 → 改欄位 → 發布 → +user 新增時可以選它 → +tenant 退役目前版本 → +user 不能再以它新增(已送出的照常看)。
20. **兩級核准與主管解析**:申請人在沒有主管的下層組織送出 → 往上找到上層組織的主管 → 主管核准 → 人資(角色來源)核准 → 已完成。
21. **退回修改 → 再送 → 駁回**:主管退回(理由必填)→ 申請人改完再送(修訂 +1、從第一關重審)→ 主管駁回 → 已駁回、不能再改。
22. **審核者停用 → 阻擋 → 改派**:審核者被停用 → 單被阻擋 → 流程管理者在阻擋清單改派給另一人 → 新審核者核准 → 已完成。
23. **核准後作廢 → 複製為新單 → 重審**:綁流程的已完成單沒有「編輯」只有「作廢」→ 作廢(理由必填)→ 複製為新單 → 送出重新審核。
24. **三部門平行**:初審後財務 / 法務 / 採購三條分支同時審;採購那條因承辦人停用而阻擋、改派,財務與法務照審;三條都通過才匯合,原部門確認核定。
25. **代理人**:審核者在個人設定設代理人 → 代理期間輪到他的任務改派給代理人、代理人在待我審核看得到並核准;會簽多位審核者委託同一人只出一張待辦、一票作用到所有被代理者;刪除代理後不再改派。
26. **知會**:關卡的知會對象在該關通過 / 被跳過時收到通知;整個流程的知會對象在單據完成、駁回、作廢時收到;退回修改不知會,重送後再通過該關才再知會。
27. **批次核准**:待我審核勾多筆一次核准,每一筆各自處理;已不在你手上的那一筆失敗、其他筆照常,結果對話框列出成功數與失敗原因。
28. **指定組織跳過與自動通過**:申請人屬於指定組織的關卡直接跳過(不含下層時看的是申請人自己的所屬組織);申請人是審核者、或審核者已在前關核准過,開了自動通過的關卡記成他核准。
29. **通知中心**:流程動作產生站內通知 → 通知鈴的未讀數與清單看得到 → 點一則標已讀並開連結、全部標已讀;同一事件不重複通知。

# 怎麼驗:每條劇本用哪一頁、哪個帳號、什麼步驟

示範模組、三個示範表單與申請中心都有真頁面,29 條劇本**全部可以在畫面上跑完**(唯一的例外是劇本 1 的跨版本那半條,見該節)。

**寫或改一條劇本的前置 / 預期之前,先對一次規則正本**:劇本 8 / 9 / 12 / 14 / 17 最容易寫成「照字面做驗不出來」,要對齊的規則是 —— 可見範圍是**所有**所屬組織的聯集(ADR-0005)、最後一個所屬組織不可移除(`LAST_ORG`)且檢查在擁有者保護之前、管理範圍算**全部**啟用中角色、授予要過資格檢查(ADR-0003)。E2E 的 spec 開頭註解與本文件的前置一致;**畫面文案一律從 zh-TW 字典(`packages/i18n/messages/zh-TW/admin.json`)原樣複製**,不要憑印象寫(「保留所有角色授予」不是「全部保留」)。

| ----------- | ----------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **root**    | seed 的超級管理員(帳號 `root`,屬根組織;ADR-0002)                                                                                                | 部署時由 seed 建立,密碼在該環境的 Secret(`ROOT_ADMIN_*`,見 `docs/env-registry.md`)                                                                                                                                                                                                                                                  |

### 組織與角色的前置

1. **root** 登入 → 組織管理 → 開通租戶,建「租戶A」與 **+tenant**(劇本 16 一併驗)。
2. **+tenant** 登入 → 組織管理 → 在租戶A 底下建「南港店」「內湖店」兩個分店。
3. **+tenant** → 使用者管理 → 建 **+user**(所屬組織:南港店);順手把 **+tenant 自己也加入南港店**(多一個所屬組織)——劇本 2 / 4 要兩個帳號的可見範圍有交集才比得出差異;劇本 17 也靠它(+tenant 只屬租戶頂層的話,「移出租戶」會先撞 `LAST_ORG`)。劇本 12 反而要在資料建完後把他移出南港店,見該節。
   **「加進某個組織」有兩個入口**:組織管理 → 選「南港店」→「成員」分頁 →「加入成員」,一次可多選。兩個入口做的是同一件事(對每個人的所屬組織加一筆、寫同一筆 `user.add-org` 稽核),挑順手的用;**移出**只有使用者管理那一個入口。
4. **+tenant** → 角色管理 → 建「客服」角色(擁有組織 = 租戶A),權限矩陣勾示範家族(示範群組 → 示範次群組 → 示範模組1 與其三個隱藏頁、示範模組2 與其三個隱藏頁),各給 `view` / `create` / `edit` / `delete`;**先不要勾** `show-internal-note` / `edit-internal-note` / `show-tips` / `show-history`(劇本 5 / 6 會一項一項打開)。指派給 +user。

### 示範資料的兩個已知限制(會影響步驟,不是 bug)

- **seed 的 10 筆示範資料全部落在根組織**(`apps/db-migrator/seeds/base/demo-items.ts`;`orgs` 種子只有根組織一筆,租戶是開通出來的、各環境 id 不同,seed 引用不到)。所以 **+tenant / +user 一登入,兩支示範模組的列表都是空的** —— 那是對的,不是壞掉。凡是要比對「看得到 / 看不到」的劇本(2 / 3 / 4 / 8 / 12),**都要先用租戶帳號自己新增幾筆**。
- **seed 資料的建立者是固定的假 id**,所以 root 看 seed 那 10 筆時,詳情頁的「建立者」一律顯示「—」。要在畫面上看到人名,就自己新增一筆。

### 劇本 2 / 12 的共同前置資料

以下兩條劇本都要靠「同一個可見範圍裡、建立者與所屬組織都不同」的資料才驗得出來,**先照這個順序建**:

1. **+user**(當前組織 = 南港店)在示範模組1 新增 **2 筆**(名稱好認一點,例如「南港-自建1 / 2」)。
2. **+tenant** 把當前組織切到**南港店**,新增 **1 筆**(「南港-他人」)。
3. **+tenant** 把當前組織切回**租戶頂層**,新增 **1 筆**(「頂層-他人」)。
4. 示範模組2 也照樣各建一筆(劇本 3 的對照組要用)。

**分類欄的先決條件**:示範模組1 的分類下拉來自欄位管理的「示範分類」,`fieldCategories` / `fields` 兩個端點都掛在 **`system.field-manager.view`** 底下。**「客服」角色沒有這個權限**,所以 +user 會看到:**列表沒有分類篩選、表單的分類欄退成唯讀並說明原因**(原值保留)。這本身就是劇本 2 / 12 要一起確認的畫面;要讓 +user 選得了分類,就在角色矩陣另外給他欄位管理模組與 `view` 權限。

## 逐條劇本

### 劇本 1 — wildcard 涵蓋未來(同層)

- **用哪一頁**:角色管理 → 編輯「客服」→「權限設定」分頁(權限矩陣)
- **帳號**:+tenant
- **E2E**:`apps/e2e/src/specs/scenario-01-wildcard.spec.ts`(手動觸發,見下方「E2E 怎麼跑」)

1. 展開示範模組1 的節點,勾它的「全部(\*)」→ 同層的 view / create / edit / delete / 內部備註兩筆一起被連動勾起(M-03 / M-04)。
2. 往下看**編輯頁**節點:它的「全部(\*)」與 `show-history` **沒有**被勾起來。
3. 儲存、重新進入 → 勾選狀態一致。

**預期**:wildcard 只代表**該模組自己這一層**;子模組(隱藏頁)要各自勾自己的 `*`。資料庫只存一筆 `demo.sub.sample-one.*`(UI 看不到筆數,以 api 測試為準)。

**在畫面上驗不到的半條**:「下一版 seed 對示範模組1 新增權限 → 不改角色即擁有」要跨版本,由 api 測試覆蓋(`apps/api/src/demo-items-one/demo-items-one-permissions.test.ts`、`apps/api/src/permission/permission.test.ts`)。

### 劇本 2 — 資料範圍規則

- **用哪一頁**:「資料範圍」頁(建規則)+ 示範模組1 列表 / 詳情(看結果)
- **帳號**:規則用 **root**(資料範圍是根組織專屬模組,+tenant 的側欄沒有它 —— 見劇本 16);結果用 **+user**
- **前置**:上面「劇本 2 / 12 的共同前置資料」四筆

- **前置**:+tenant 在租戶A 底下建「東區」,把**南港店搬到東區底下**;另建兩個角色指派給 +user —— 「南港店長」(擁有組織 = 南港店)、「東區督導」(擁有組織 = 東區);「客服」(擁有組織 = 租戶A)照舊

| 角色     | 擁有組織 | 移除南港店後                         | (b)  | (c)  |
| -------- | -------- | ------------------------------------ | ---- | ---- |

| 客服     | 租戶A    | 內湖店仍在子樹內,不失去資格          | —    | —    |

## E2E 怎麼跑

有 spec 的劇本**不必再人工走一次**,但 E2E **只在手動觸發時跑**(不進每個 PR 的 CI,理由見 TEST-05):

```bash
pnpm e2e                       # 本機全部(harness 會自己 build、起 Mongo / api / admin)
E2E_GREP="劇本 7" pnpm e2e     # 只跑某一條
gh workflow run e2e.yml --ref <分支> -f grep="劇本 7"   # CI(.github/workflows/e2e.yml)
```

Windows 上用 PowerShell 設變數:`$env:E2E_GREP="劇本 7"; pnpm e2e`(Bash 的 `E2E_GREP=… pnpm e2e` 前綴會被 agent 的 worktree 守衛擋下,見 `apps/e2e/README.md`)。

harness、前置資料與寫法見 `apps/e2e/README.md` 與 `docs/standards/testing/testing.md` 的 TEST-11。
新增劇本而還沒有 spec 時,「一頁看完」表的 E2E 欄寫「尚未」,照本文件人工驗收;補上 spec 時同時改掉這一欄。

**額外一條(不在 29 條內)**:模組與權限頁 —— root 停用「示範模組2」→ +tenant 的側欄少一項;重新啟用只開這一個節點(停用父模組時整棵子樹視同停用)。
